# Lost Update — 락 없는 동시 주문 실측

측정 시점: 2026-08-07 · 코드 상태: `phase2-security` + N+1 개선 (`@Version` 이전)
측정 방법: `ExecutorService` + `CountDownLatch`로 동일 계정에 동시 주문 100건

> 이 문서는 **결함이 살아 있는 상태**의 기록이다. 테스트 코드는 이 시점에 커밋하지 않았다 —
> 정합성을 단언하면 실패하고, 실패하는 테스트를 커밋하면 `./gradlew build`가 깨진다.
> 테스트는 `@Version`과 같은 커밋에 들어간다.

---

## 시나리오

| 항목 | 값 |
|---|---|
| 초기 포인트 | 1,000,000.00 |
| 상품 단가 | 1,000.00 |
| 동시 스레드 | 100 (스레드 풀 100) |
| 각 스레드 | **서로 다른 상품**을 1개씩 주문 |
| 기대 최종 포인트 | 900,000.00 |

**스레드마다 다른 상품을 주문하는 이유** — 같은 상품이면 `(customer_id, product_id)` 복합 UNIQUE에
걸려 제약 위반이 먼저 터지고, 정작 보려는 **고객 포인트의 경합**이 그 뒤에 가려진다.
경합 지점을 `Customer.customerPoint` 하나로 좁힌다.

**테스트 메서드에 `@Transactional`을 붙이지 않는다.** 붙이면 모든 스레드가 테스트의 트랜잭션
하나를 공유해 동시성 자체가 사라진다 — 통과해도 아무것도 증명하지 못한다.

## 결과 — 3회 반복

```
[동시성] 스레드 100 · 성공 100 · 실패 {} · 186ms
[동시성] 최종 포인트 988000.00 · 기대 900000.00 · 차이 88000.00

[동시성] 스레드 100 · 성공 100 · 실패 {} · 187ms
[동시성] 최종 포인트 988000.00 · 기대 900000.00 · 차이 88000.00

[동시성] 스레드 100 · 성공 100 · 실패 {} · 182ms
[동시성] 최종 포인트 988000.00 · 기대 900000.00 · 차이 88000.00
```

| 지표 | 값 |
|---|---|
| 주문 성공 | **100 / 100** (예외 0건) |
| 실제 차감액 | 12,000.00 |
| 차감됐어야 할 금액 | 100,000.00 |
| **증발한 차감** | **88,000.00 (88건)** |
| 소요 | 182~187ms |

**고객은 상품 100개를 받고 12개 값만 냈다.** 예외는 한 건도 발생하지 않았다 —
애플리케이션은 100건 전부 정상 처리했다고 보고한다.

### 원인

`OrderService.placeOrder`는 고객을 읽고(`findCustomer`) → 포인트를 빼고(`usePoint`) →
커밋 시 더티 체킹이 `UPDATE customers SET customer_point = ?`를 낸다.
읽기와 쓰기 사이에 다른 트랜잭션이 끼어들면 **나중 커밋이 먼저 커밋의 차감을 덮어쓴다.**
`Customer.usePoint`가 잔액을 스스로 검사하지만, 그 검사는 **자기가 읽은 값**에 대한 것이라
동시성 앞에서는 무력하다. 불변식을 엔티티에 넣은 것과 별개의 문제다.

### 손실량이 3회 모두 정확히 같은 이유

레이스인데 결과가 결정적이라 의심스러웠다. 원인은 **HikariCP 기본 최대 풀 크기 10**이다
(설정하지 않아 기본값). 스레드는 100개지만 **DB 트랜잭션은 한 번에 최대 10개**만 진행되므로
경합 폭이 10으로 고정되고, 그 결과 살아남는 차감 수도 매번 비슷하게 수렴한다.

> 즉 이 수치는 **커넥션 풀 크기에 종속**된다. 풀을 키우면 손실이 커지고 줄이면 작아진다.
> 절대값이 아니라 **"락이 없으면 차감이 소실된다"는 사실**이 이 측정의 결론이다.
> 풀 크기 튜닝은 근거가 필요한 항목이라 Phase 6 부하 측정과 함께 다룬다 (`PLAN.md`).

## 측정 장치에서 먼저 걸린 것 — 배리어가 스스로 교착했다

첫 실행의 소요 시간은 **30,213ms**였다. 이 값이 `ready.await(30, SECONDS)`의 타임아웃과
소수점까지 맞아떨어져 확인해보니, **아무 일도 일어나지 않은 30초**였다.

스레드 풀을 32로 두고 래치는 100을 기다리게 했다. 먼저 실행된 32개는 `start.await()`에서
대기하는데, 나머지 68개는 **큐에 갇혀 `ready.countDown()`을 호출하지 못한다.**
`ready`는 영원히 0이 되지 않고, 타임아웃이 만료된 뒤에야 풀렸다.

- 풀 크기를 스레드 수와 같게 맞췄다 → **186ms**
- `ready.await(...)`의 **반환값을 단언**하도록 고쳤다. 타임아웃으로 풀리면 동시성이 성립하지
  않은 것이므로 그 실행의 수치는 버려야 한다

> Lost Update 자체는 두 경우 모두 88,000으로 동일하게 재현됐다. 그래서 **결함 재현이라는 목적만
> 보면 첫 실행도 "성공"이었고, 30초를 그대로 소요 시간으로 기록했을 것이다.**
> 이 수치는 Phase 3 항목 7(낙관적 vs 비관적 처리량 비교)의 기준이 된다 — 거기서 30초와 186초를
> 비교했다면 결론이 통째로 뒤집혔다.
