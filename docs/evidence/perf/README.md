# Phase 6 성능 측정 자료

원시 출력을 그대로 보존한다. **요약본으로는 나중에 다른 각도로 재해석할 수 없다.**
각 `.txt` 파일 상단에 측정 조건(커밋 해시·작업트리 상태·호스트/Docker 사양·이미지 태그·
워밍업 여부·DB 초기화 방식)이 박혀 있다.

## ★ 측정 세트가 둘이다 — 섞지 않는다

이 디렉터리에는 **서로 다른 두 머신의 측정**이 들어 있다. 파일명 접두사로 구분한다.

| 세트 | 파일 | 머신 |
|---|---|---|
| **A (macOS)** | `before-*`, `sweep-pool*`, `sweep-threads*`, `sweep-repeat*` | macOS · Apple M5(ARM) · Docker VM 10CPU/7GB |
| **B (Windows)** | **`sweep-win-*`** | Windows 10 · x86_64 · **Docker Desktop WSL2** · 12CPU/7.7GiB |

> **비교는 각 세트 안에서만 성립한다.** 사양도 OS도 다르고, B는 Docker가 WSL2를 경유해
> I/O 특성이 다르다. **노이즈 차이가 아니라 다른 환경이다.**
> 보고서에서도 두 세트의 수치를 같은 표에 넣지 않는다.
>
> 실제로 **두 세트에서 결론이 뒤집혔다** — 상세는 `DECISIONS.md` 26절.
> 반복 편차부터 다르다: A 0.65ms / B **1.91ms**.

## 세트 A — 측정 환경 (macOS)

| 항목 | 값 |
|---|---|
| 호스트 | macOS (Darwin 25.5.0) · Apple M5 · 10코어 · 16GB |
| Docker VM | CPU 10 · MEM 7GB |
| DB | `postgres:16-alpine` (같은 머신, 같은 compose 네트워크) |
| 부하 생성기 | `grafana/k6:2.1.0` — **같은 머신에서 실행** |
| DB 초기화 | 각 측정 직전 `app` 재기동 (`ddl-auto=create`) |

> **해석 제한** — 앱·DB·부하 생성기가 **한 머신의 자원을 나눠 쓴다.**
> 절대 수치(TPS·p95)는 이 조건의 것이고, 실제 배포 환경의 상한이 아니다.
> Phase 3에서 "Lost Update 손실량 88,000은 커넥션 풀 크기가 만든 값"이라고 적은 것과 같은 제한이다.
> **의미가 있는 것은 같은 조건에서의 상대 비교**다.

## 세트 B — Windows / WSL2 (2026-08-08)

| 항목 | 값 |
|---|---|
| 호스트 | Windows 10 (19045) · x86_64 |
| Docker | Docker Desktop 29.1.2 · **WSL2 백엔드** · CPU 12 · MEM 7.7GiB |
| 셸 | Git Bash (MinGW) |
| 커밋 | `sweep-win-repeat` `50cd7ef` · `sweep-win-pool` `3178646` · `sweep-win-threads` `40fa375` |

> ⚠️ `win-pool`·`win-threads` 실행 당시 `sweep.sh` 의 409·5xx 컬럼 추가분이 **미커밋**이었다.
> 각 파일 하단 [사후 주석] 참조. 측정값에는 영향이 없다(리포팅 컬럼만 추가).

### 반복 편차 (`sweep-win-repeat.txt`)

p95 **14.25 / 13.49 / 15.40ms → 폭 1.91ms** (세트 A는 0.65ms — **약 3배**).
req/s 는 폭 1%로 안정적이고 **p95만 흔들린다.**

### HikariCP 풀 크기 (`sweep-win-pool*.txt`)

| 풀 | 성공률 | p95 | req/s | 409 | **409 비율** | 5xx |
|---|---|---|---|---|---|---|
| 2 | 100% | **46.32ms** | **710** | 46 | **0.08%** | 0 |
| 5 | 100% | 16.57ms | 1,002 | 262 | 0.34% | 0 |
| 10 (기본) | 100% | 14.72ms | 1,003 | 500 | 0.65% | 0 |
| 20 | 100% | 14.82ms | 1,011 | 743 | 0.96% | 0 |
| 40 | 100% | 15.54ms | 991 | 754 | **0.99%** | 0 |

**풀 5~40 은 p95 폭 1.85ms 로 편차(1.91ms) 안 — 변별 불가.**
**풀 2 는 이 환경에서 병목이다** (세트 A에서는 최선이었다).
**409 비율만 단조로 12배 증가한다.**

### Tomcat 스레드 (`sweep-win-threads*.txt`)

| 스레드 | 성공률 | p95 | req/s | 409 | **409 비율** | 5xx |
|---|---|---|---|---|---|---|
| 10 | 100% | **7.22ms** | **1,081** | 742 | 0.90% | 0 |
| 25 | 100% | 13.34ms | 1,013 | 691 | 0.88% | 0 |
| 50 | 100% | 12.40ms | 1,023 | 557 | 0.71% | 0 |
| 100 | 100% | 12.16ms | 1,030 | 555 | 0.70% | 0 |
| 200 (기본) | 100% | 14.79ms | 1,012 | 662 | 0.85% | 0 |

**스레드 10 이 유의하게 좋다** (세트 A에서는 유일하게 나빴다).
**409 비율은 경향이 없다** — 풀에는 반응하고 스레드에는 반응하지 않는다.
이 대비가 "409는 DB 동시성 폭을 재는 특이 지표"라는 해석의 근거다 (`DECISIONS.md` 26절).

### 5xx 0건

**양쪽 스윕 10회 전 구간에서 500이 한 건도 없다.** 세트 A의 풀 40에서 `resp_5xx: 8` 이던 것
(24절의 동시 첫 주문 결함, `278b077`에서 교정)이 **다른 머신·다른 부하 프로파일에서도
재발하지 않음**을 확인했다.

### HA 다중 인스턴스 (`win-ha-load*.txt`)

`docker-compose.ha.yml` — nginx + app 2대 + 공유 PostgreSQL. 대상은 LB(`http://lb:80`).

| 구성 | 파일 | req/s | p95 | 409 비율 |
|---|---|---|---|---|
| 직접 1대 (LB 없음, 풀 10) | `sweep-win-pool-10.txt` | 1,003 | 14.72ms | 0.65% |
| **LB + 1대** (대조) | `win-ha-load-1instance.txt` | 981 | 18.68ms | 2.02% |
| **LB + 2대 (HA)** | `win-ha-load.txt` | **814** | **46.96ms** | **2.33%** |

**처리량이 늘지 않고 줄었다(−19%).** 대조를 두어 원인을 갈랐다 —
**LB 홉은 −2%로 미미하고, 하락의 대부분은 두 번째 인스턴스가 만든다**(981 → 814).
12 vCPU 하나 위에서 app 2개 + nginx + postgres + k6가 전부 도는 조건이기 때문이며,
이 README 최상단의 해석 제한이 정면으로 드러난 사례다.

> ⚠️ **첫 측정 한 쌍은 폐기했다.** 두 측정 사이에 DB를 초기화하지 않아 대조가 오염됐다.
> 위 값은 각 측정 직전에 초기화한 재측정분이다. 경위는 `JOURNAL.md` 2026-08-08.

**사전 등록한 409 예측은 빗나갔고(`ha-prediction.md`), 그 실패가 26절의 인과적 일반화를
반증했다.** `LB + 1대`는 DB 동시성 폭이 단일과 같은데도 409가 3.1배였다.
판정과 재검토는 `ha-prediction.md` 하단, 정정은 `DECISIONS.md` 26·27절.

| 캐시·ETag의 근거와 미측정 범위 | `DECISIONS.md` **25절** |
| 스윕 해석과 기본값을 바꾸지 않은 이유 | `DECISIONS.md` **26절** |
