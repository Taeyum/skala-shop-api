# Phase 6 성능 측정 자료

원시 출력을 그대로 보존한다. **요약본으로는 나중에 다른 각도로 재해석할 수 없다.**
각 `.txt` 파일 상단에 측정 조건(커밋 해시·작업트리 상태·호스트/Docker 사양·이미지 태그·
워밍업 여부·DB 초기화 방식)이 박혀 있다.

## 측정 환경 (전 측정 공통)

| 항목 | 값 |
|---|---|
| 호스트 | macOS (Darwin 25.5.0) · Apple M5 · 10코어 · 16GB |
| Docker VM | CPU 10 · MEM 7GB |
| DB | `postgres:16-alpine` (같은 머신, 같은 compose 네트워크) |
| 부하 생성기 | `grafana/k6:2.1.0` — **같은 머신에서 실행** |
| DB 초기화 | 각 측정 직전 `app` 재기동 (`ddl-auto=create`) |

> **해석 제한** — 앱·DB·부하 생성기가 **한 머신의 자원을 나눠 쓴다.**
> 절대 수치(TPS·p95)는 이 조건의 것이고, 실제 배포 환경의 상한이 아니다.
> Phase 3에서 "Lost Update 손실량 88,000은 커넥션 풀 크기가 만든 값"이라고 적은 것과 같은 제한이다.
> **의미가 있는 것은 같은 조건에서의 상대 비교**다.

## 설정 스윕 (커밋 `99ff4db`, load.js VUS=50 / 45초)

### 반복 편차 먼저 (`sweep-repeat.txt`)

같은 설정(`DB_POOL_SIZE=10`)을 3회 반복: p95 **6.26 / 5.75 / 5.61ms → 폭 0.65ms**.
**이 값보다 작은 차이는 설정 효과로 읽지 않는다.**

### HikariCP 풀 크기 (`sweep-pool*.txt`)

| 풀 크기 | 성공률 | p95 | req/s | 409 충돌 |
|---|---|---|---|---|
| 2 | 99.99% | **3.54ms** | 1,163 | 40 |
| 5 | 99.99% | 3.95ms | 1,156 | 245 |
| 10 (기본) | 99.99% | 4.67ms | 1,142 | 404 |
| 20 | 99.99% | 5.54ms | 1,119 | 592 |
| 40 | 99.99% | 5.27ms | 1,134 | 469 |

**폭 2.00ms — 반복 편차(0.65ms)의 3배.** 단조 증가이므로 신호로 본다.
풀이 커질수록 409 충돌도 함께 늘어 "동시 실행 폭이 넓어져 경합이 는다"는 설명과 일치한다.

### Tomcat 스레드 (`sweep-threads*.txt`)

| 스레드 | 성공률 | p95 | req/s |
|---|---|---|---|
| 10 | 100% | **6.52ms** | 1,090 |
| 25 | 100% | 4.79ms | 1,137 |
| 50 | 100% | 4.82ms | 1,148 |
| 100 | 100% | 4.72ms | 1,121 |
| 200 (기본) | 100% | 5.37ms | 1,119 |

**10만 측정 가능하게 나쁘고, 25 이상은 전부 반복 편차 안이다.**

## 이 측정이 찾아낸 결함

**동시 첫 주문의 제약 위반이 500으로 나가고 있었다** (커밋 `278b077`에서 교정).
집계로는 "성공률 99.99%"라 묻혀 있었고, 스윕에서 `resp_5xx`를 따로 세면서 드러났다.
상세는 `DECISIONS.md`·`JOURNAL.md`.

## 아직 하지 않은 것

- 캐시(`@Cacheable`) 적용 전/후 측정 — 구현과 기능 검증은 끝났으나 **성능 효과는 미측정**
- HTTP 캐시 헤더의 전송량 절감 측정
- 튜닝값 확정 후 재측정 및 비교표
- `graceful shutdown` k6 재검증 (Phase 5에서 미검증으로 남긴 항목)
- HA 다중 인스턴스 처리량 비교
