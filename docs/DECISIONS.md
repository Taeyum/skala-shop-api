# 설계 의사결정 기록

스펙과 다르게 구현한 모든 항목의 근거. **보고서의 원본 자료가 되므로 작업하면서 계속 채운다.**

형식: 무엇을 / 왜 / 트레이드오프

---

## 1. Customer PK를 자연키에서 대리키로 전환

**스펙**: `String customerId`를 PK로 사용
**변경**: `Long id`를 PK로, `customerId`는 UNIQUE NOT NULL

**근거**
- 자연키는 변경 가능성이 있다. 고객이 ID를 바꾸면 이를 참조하는 모든 FK를 갱신해야 한다
- 문자열 PK는 인덱스 크기가 크고, 자식 테이블 FK로 전파되면 저장 공간과 조인 비용이 증가한다
- 대리키는 비즈니스 의미가 없어 도메인 규칙 변경에 영향받지 않는다

**트레이드오프**: 조회 시 `customerId`로 한 번 더 찾아야 한다. UNIQUE 인덱스가 있어 비용은 무시할 수준.
**API 영향**: 없음. URI는 `/api/customers/{customerId}` 그대로 유지.

## 2. OrderItem에 결제 총액(orderedAmount) 스냅샷 추가

**스펙**: `id`, `customer`, `product`, `quantity`만 존재
**변경**: `orderedAmount` (현재 보유 수량에 대한 결제 총액 스냅샷) 추가

**근거** — 스펙대로면 환불 금액이 틀린다:
```
1) 15,000원에 2개 주문      → 30,000 차감 (잔액 970,000)
2) 관리자가 50,000원으로 인상
3) 1개 취소                 → 50,000 환불 (잔액 1,020,000)  ← 원금 초과
```
주문·결제 도메인에서 가격은 **이력성 데이터**다. 현재 값을 참조하면 과거 거래가 왜곡된다.

**트레이드오프**: 정규화 관점에서 중복이지만, 이력 보존이 목적이므로 의도된 비정규화.
**API 영향**: 없음. 응답의 `productPrice` 필드는 그대로.

### 실측 (2026-08-07, Phase 1 2단계)

위 시나리오를 개선 전후로 각각 돌렸다. E2E는 가격을 바꾸지 않아 이 결함을 통과시킨다
(`REVIEW.md` "E2E가 검출하지 못하는 것").

| | 1개 취소 후 잔액 | |
|---|---|---|
| 개선 전 (`2adfc0c`) | **1,020,000** | 현재가 50,000 환불 → 원금을 20,000 **초과** |
| 개선 후 | **985,000** | 주문가 15,000 환불 → 정상 |

### 왜 단가가 아니라 총액인가

**단가 스냅샷(`orderedPrice`)으로 출발했다가 총액(`orderedAmount`)으로 바꿨다.**

`(customer_id, product_id)` 복합 UNIQUE 때문에 고객당 상품은 **1행**이고, SPEC 3절이
"재주문 시 수량 누적(신규 행 생성 아님)"을 계약으로 요구하므로 **여러 주문이 한 행에 병합된다.**
병합된 행에서는 단가로 결제 총액을 복원할 수 없다.

```
40,000을 3개에 결제 → 단가 13,333.33 저장 (scale 2)
                      이 순간 "40,000"이라는 사실이 소실된다
                      13,333.33 × 3 = 39,999.99   ← 0.01 증발
```

**"마지막 취소에서 잔여를 보정한다"는 대안은 성립하지 않는다.** 보정하려면 원래 총액을 알아야 하는데,
그 정보는 취소 시점이 아니라 **저장 시점에 이미 사라져 있다.** `(13,333.33, 3)`에서 40,000을 복원할
방법이 없으므로 취소 시점에 어떤 로직을 넣어도 소용없다. 보정하려면 총액을 저장해야 하고, 그것이 곧 지금 안이다.

**scale을 4로 올리는 것도 해법이 아니다.** 13,333.3333으로 저장해도 7로 나누는 조합에서 같은 잔여가
생긴다 — 유리수 나눗셈의 잔여는 scale로 없앨 수 없고 줄어들 뿐이다. 게다가 금액 컬럼의 scale이 2가
아닌 것 자체가 설명 부담이며, 그 답이 "나눗셈 때문"이면 근본 해결이 아님을 스스로 드러낸다.

**단가 스냅샷이 실무 표준인 이유는 주문 건마다 행이 분리돼 있어 `단가 × 수량`이 그 행의 결제액과
일치하기 때문이다.** 단가라는 형태 자체가 표준인 것이 아니다. 병합을 계약으로 요구하는 이 구조에서는
총액이 올바른 표현이며, 실무 표준에서의 이탈이 아니라 **스펙이 강제한 구조에 맞춘 적응**이다.

### 환불 계산

| 상황 | 계산 |
|---|---|
| 전량 취소 | `orderedAmount` 전액. **나눗셈이 없어 반올림이 개입하지 않는다** |
| 부분 취소 | `orderedAmount × 취소수량 ÷ 보유수량` (곱한 뒤 나눔 — 반올림 1회, `RoundingMode.DOWN`) |

남은 총액은 **재계산이 아니라 차감**한다. 재계산하면 반올림이 매번 새로 일어나 오차가 누적되지만,
차감하면 잔여가 잔액에 남아 다음 취소로 이월돼 **환불 합계가 결제 총액과 항상 일치한다.**

`DOWN`을 쓰는 이유 — `HALF_UP`도 합계는 정확하고 잔여가 음수가 되지도 않는다(`orderedAmount`가
scale 2 값이라 그 이하를 scale 2로 반올림해도 초과할 수 없다). 다만 `HALF_UP`은 개별 환불액이 정확한
몫을 **초과**할 수 있다(7개/10,000에서 6번째 취소가 1,428.58, 정확한 몫은 1,428.57…).
`DOWN`은 각 취소가 몫을 넘지 않고 잔여를 마지막에 몰아준다.

**실측** — 15,000×3 + 10,000×4 = 85,000을 7개에 결제(85,000÷7 = 12,142.857…로 나눠떨어지지 않음)한 뒤
1개씩 7회 취소:

```
927,142.85 → 939,285.70 → 951,428.56 → 963,571.42 → 975,714.28 → 987,857.14 → 1,000,000.00
                                                        마지막 취소가 12,142.86 (누적 잔여 포함)
```

원금 1,000,000으로 **정확히 복귀**한다.

> **한계** — 부분 취소는 평균 단가로 환불되므로 "어느 시점에 산 물건을 취소하는가"를 구분하지 못한다.
> 정확히 하려면 주문 건별 행(`Order` + `OrderLine`)이 필요하고, 그러면 행마다 결제액이 하나씩
> 대응하므로 **단가 스냅샷으로 충분해진다.** 현재 구조가 "주문 이력"이 아니라 "현재 보유 수량"이라는
> 한계와 같은 뿌리다 (13절).

## 3. 금액 타입을 Double에서 BigDecimal로

**스펙**: `Double productPrice`, `Double customerPoint`
**변경**: `BigDecimal`, `@Column(precision = 19, scale = 2)`

**근거**: 부동소수점은 십진 소수를 정확히 표현하지 못한다 (`0.1 + 0.2 != 0.3`). 금액 계산에서 오차가 누적되면 잔액이 틀어진다.

**주의사항**
- `new BigDecimal(0.1)` 금지 → `BigDecimal.valueOf(0.1)` 또는 `new BigDecimal("0.1")`
- 비교는 `compareTo()`. `equals()`는 scale까지 비교해 `1.0 != 1.00`
- 나눗셈은 `RoundingMode` 필수

**API 영향**: 필드명·URI는 그대로. 다만 **JSON 숫자 표기가 바뀐다** — 실측 결과
`1000000.0` → `1000000.00`, `15000.0` → `15000.00`. scale 2가 직렬화에 그대로 드러나기 때문이다.
필드명이 아니라 값의 표기이고 숫자로 파싱하면 동일하므로 계약 위반은 아니지만,
"직렬화 결과가 동일하다"는 당초 예상은 틀렸다. 금액에 소수 2자리가 보이는 편이 오히려 자연스럽다고
판단해 그대로 둔다.

> **강의 자료 예시와 표기가 다른 이유** — 자료의 응답 예시는 `"customerPoint": 970000`처럼 정수로 적혀
> 있는데 이 구현은 `970000.00`으로 나간다. 자료가 `Double`을 쓰기 때문이고, 우리는 금액을
> `BigDecimal(scale = 2)`로 바꿨기 때문이다. **JSON 숫자는 표기 형식이 정해져 있지 않고**
> `970000`·`970000.0`·`970000.00`은 모두 같은 수다. 필드명·구조·URI는 자료와 동일하며,
> 클라이언트가 숫자로 파싱하면 차이가 없다. 표기를 자료에 맞추려면 금액을 다시 `Double`로 되돌리거나
> 직렬화 시 스케일을 죽여야 하는데, 둘 다 정확성을 표기 일치와 맞바꾸는 것이라 하지 않는다.

## 4. 기술 계층 대신 도메인 기준 패키지 구조

**스펙**: `controller/`, `service/`, `repository/`, `data/`
**변경**: `product/`, `customer/`, `order/`, `global/`

**근거**: 모듈러 모놀리스. 도메인 폴더 하나가 미래의 마이크로서비스 하나에 대응한다. 기술 계층 구조는
서비스 분리 시 모든 폴더를 헤집어야 하지만, 도메인 구조는 폴더째 떼어낼 수 있다.
"Monolith First" — 처음부터 쪼개지 않고, 경계만 명확히 그어 필요할 때 분리한다.

**트레이드오프**: 강의 자료의 폴더 구조와 다르다. 클래스명과 API는 100% 동일하게 유지해 대조 가능성을 확보.

### OrderItem을 왜 별도 도메인으로 두었나

주문은 고객·상품 **양쪽에 걸쳐** 있어 어디에 두든 근거가 필요하다.

- `OrderItem`은 `quantity`·`orderedAmount`라는 **고유 속성**을 가진다. 속성 없는 연결 테이블이면
  한쪽에 붙여도 되지만, 결제 총액을 들고 있는 이상 독립 개념으로 볼 근거가 있다
- `customer/`에 두면 상품 도메인이 고객 도메인 내부를 참조해야 하고, `product/`에 두면 반대가 된다.
  어느 쪽이든 **한 도메인이 다른 도메인의 내부 구조에 묶인다**
- 별도 도메인으로 두면 `order → customer`, `order → product` **단방향**으로 정리된다

### 의존 방향 — 못박아 둔다

```
        order
        ╱    ╲
   customer  product      (customer ↔ product 사이에는 의존이 없다)
```

**`customer`와 `product`는 `order`를 알지 않는다.** 역방향이 생기는 순간 순환이 된다.

이 규칙 때문에 `GET /api/customers/{customerId}`(고객 정보 + 보유 상품)의 조립을 **주문 도메인이 맡는다.**
고객 도메인이 조립하면 `customer → order` 의존이 생겨 순환이 되기 때문이다. URI는 고객 쪽이지만
읽는 데이터의 중심은 주문 목록이므로 위치도 어색하지 않다.

각 Service의 의존은 다음이 전부다.

| Service | 의존 |
|---|---|
| `ProductService` | `ProductRepository` |
| `CustomerService` | `CustomerRepository` |
| `OrderService` | `OrderItemRepository` + `CustomerService` + `ProductService` |

**검증**: 어떤 도메인도 다른 도메인의 Repository를 import하지 않는다. `product/`·`customer/`는 다른
도메인을 아예 참조하지 않고, `order/`만 두 도메인의 **엔티티**를 참조한다 — JPA 연관관계라 불가피하다.

### `findCustomer`·`findProduct`가 엔티티를 반환하는 것 — 알고 남겨둔 경계

다른 도메인에 노출되는 이 두 메서드는 엔티티를 그대로 반환한다. **MSA로 분리하면 이 자리가 원격 호출
경계가 되고 엔티티는 직렬화 경계를 넘지 못한다.** 지금 DTO로 바꾸지 않는 이유는, 호출자가 이 값을
`OrderItem`의 **JPA 연관관계로 그대로 쓰기** 때문이다.

```java
OrderItem.of(customer, product, quantity, amount)   // 연관 엔티티가 필요하다
```

DTO를 반환하려면 `OrderItem`이 `Customer`·`Product` 참조 대신 `customerId`·`productId`를 들어야 한다.
그것이 곧 **ID 참조 전환**이고, `PLAN.md` Phase 7 MSA 전환 로드맵의 첫 항목이다. 지금 반쪽만 바꾸면
DTO를 받아 다시 엔티티를 조회하는 코드가 생겨 쿼리만 늘고 얻는 것이 없다. **전환은 ID 참조와 함께 간다.**

## 5. Service를 얇게, 도메인을 두껍게 — 웹 관심사 제거와 풍부한 도메인 모델

두 작업을 한 항목으로 묶는 이유가 있다. **따로 보면 각각은 평범한 리팩터링이다** — "setter를 없앴다",
"어노테이션으로 인증을 뺐다". 묶으면 하나의 방향이 된다: **Service에서 양쪽으로 밀어낸다.**
위(웹 관심사)는 Controller로, 아래(불변식)는 엔티티로. 남는 것이 Service의 진짜 일 — 흐름 조율이다.

```
       [ Phase 0 ]                          [ Phase 1 5·6단계 ]

  Controller  얇음                      Controller  인증 해결(@LoginCustomer)
       │                                     │
  Service     쿠키/JWT를 알고             Service     조회 → 도메인 호출 → 저장
              잔액도 직접 계산                 │        (흐름만 남는다)
       │                                     │
  Entity      getter/setter 덩어리       Entity      스스로 불변식을 지킴
```

### 5-1. 불변식을 엔티티 안으로 (5단계 — 완료)

**변경**: `@Setter` 전면 제거, `@NoArgsConstructor(access = PROTECTED)`, 정적 팩토리, 행위 메서드

| 불변식 | 어디서 지키는가 |
|---|---|
| 포인트는 음수가 될 수 없다 | `Customer.usePoint()` — 부족하면 `INSUFFICIENT_FUNDS` |
| 보유 수량을 초과해 취소할 수 없다 | `OrderItem.cancel()` — 초과하면 `INSUFFICIENT_QUANTITY` |
| 상품명은 비어있을 수 없고 가격은 0 이하일 수 없다 | `Product.of()` / `changeInfo()` |
| 수량과 결제 총액은 항상 함께 움직인다 | `OrderItem.addOrder()` / `cancel()` |

**근거** — setter가 열려 있으면 불변식은 **호출부의 성실함에 의존한다.** Service가 검증을 잊으면 그대로
깨진다. 검증을 데이터 옆에 두면 **어느 경로로 접근하든** 지켜진다. 실제로 `INSUFFICIENT_FUNDS`·
`INSUFFICIENT_QUANTITY`를 던지는 코드는 이제 Service에 한 줄도 없고 전부 엔티티 안에 있다.

**메서드 이름** — `addQuantity` / `reduceQuantity`를 쓰지 않았다. 이 연산들은 수량만 바꾸지 않고
`orderedAmount`를 함께 움직인다(2·3절). 수량만 다루는 것처럼 읽히는 이름을 두면 나중에 "수량만
조정하면 되는데" 하고 한쪽만 바꾸는 호출이 생긴다. **거래 한 건을 더하고 취소한다**는 뜻이 드러나도록
`addOrder(quantity, amount)` / `cancel(quantity)`로 정했다. 경위는 `JOURNAL.md` 2026-08-07.

**트레이드오프**: 테스트에서 임의 상태의 엔티티를 만들기 번거로워진다. Phase 4에서 픽스처 팩토리로 해결한다.

### 5-2. 웹 관심사를 Controller로 (6단계 — 완료)

**스펙**: `CustomerService`가 `SessionHandler`를 주입받고 `Response`를 반환
**변경**: `@LoginCustomer` ArgumentResolver로 Controller에서 인증을 해결, Service는 `customerId`만 받는다.
Service의 `Response` 반환도 제거하고 DTO를 반환한다.

**근거**: 쿠키·JWT·세션은 웹 계층 관심사다. Service가 이를 알면 ① 순수 단위 테스트가 불가능하고
② 배치·스케줄러가 같은 로직을 재사용할 수 없으며 ③ 인증 방식 변경이 도메인 로직에 파급된다.

**인증 실패를 Resolver에서 던지는 이유** — `null`을 주입하고 Service가 판단하게 하면 Service가 다시
"인증"이라는 웹 관심사를 아는 셈이 되어 이 단계의 목적이 무너진다. `@LoginCustomer`가 붙은 엔드포인트는
인증이 필수라는 선언이고, 쿠키가 없거나 토큰이 무효하면 **Service까지 내려가지 않는다.**

**옮겨간 것들**

| 무엇 | Phase 0 | 지금 |
|---|---|---|
| 쿠키에서 customerId 추출 | `CustomerService`가 `SessionHandler` 주입 | `LoginCustomerArgumentResolver` |
| 토큰 발급·쿠키 적재 | `CustomerService.loginCustomer` | `CustomerController.loginCustomer` |
| `Response` 포장 | Service 전 메서드 | Controller |
| `SessionHandler` 위치 | `common/` | `common/auth/` — 웹 인증 컴포넌트임을 위치로 드러낸다 |

**검증**: Service 두 개의 import에 `jakarta.servlet`·`springframework.web`·공통 `Response`가 하나도 없다.

> **아직 Service에 남은 검증 하나** — `loginCustomer`의 `isAnyEmpty(customerId, customerPassword)`.
> 이는 도메인 불변식이 아니라 **요청 바디에 값이 들어왔는가**를 보는 형태 검사이고,
> `findCustomer(null)` 호출을 막는 역할을 한다. Phase 2에서 Bean Validation(`@NotBlank` + `@Valid`)으로
> 바꾸면 Controller 계층으로 올라가 Service에서 사라진다.

**API 영향**: 없음. 엔드포인트·요청·응답 형태 모두 그대로다.

## 6. H2 대신 PostgreSQL 채택 (단일 DB, H2 완전 제거)

**스펙**: H2 인메모리
**변경**: PostgreSQL 16 단일. H2는 의존성·설정에서 완전히 제거. 테스트도 Testcontainers PostgreSQL

**근거** — H2로는 이 프로젝트가 목표로 하는 **측정 자체가 성립하지 않는다**:

| 항목 | H2 인메모리 | PostgreSQL |
|---|---|---|
| 커넥션 풀 튜닝 | 같은 JVM 내 호출이라 커넥션 획득 비용이 사실상 0. 풀 크기를 바꿔도 유의미한 곡선이 없다 → **근거 있는 숫자를 만들 수 없다** | 실제 TCP 연결·`max_connections` 상한이 있어 풀 크기가 처리량에 반영된다 |
| 락 실험 | MVCC 구현과 경합 프로파일이 실 DB와 달라 낙관/비관 비교 수치를 일반화할 수 없다 | 실제 격리수준·락 대기에서 측정 |
| 방언 차이 | 운영 DB에서만 터지는 쿼리를 개발 중에 못 잡는다 | 개발·테스트·운영이 같은 방언 |
| HA 다중 인스턴스 | 인스턴스마다 독립된 데이터를 가져 실증 불가 | 공유 DB로 수평 확장 실증 가능 |

> **[2026-08-08 실적] 이 줄이 실증됐다.** "실증 가능"이 예측이 아니라 결과가 됐다 —
> `docker-compose.ha.yml`로 nginx + app 2대 + 공유 PostgreSQL을 구성해
> **한 인스턴스에서 로그인한 JWT로 다른 인스턴스에서 주문이 성공**했고,
> 한 인스턴스를 내려도 **60/60 요청이 성공**했다.
>
> **H2였다면 이 검증 자체가 성립하지 않는다.** 인스턴스마다 독립된 인메모리 DB를 가지므로
> "다른 인스턴스에서 주문"은 "다른 DB에서 주문"이 되어, 무상태를 검증하는 것이 아니라
> 데이터가 갈라진 것을 확인하게 된다. **Phase 0 이전에 내린 DB 전환 결정이 여기서 열매를 맺었다.**
>
> 다만 **처리량은 늘지 않았다**(단일 머신 자원 공유). 상세는 27절.

CLAUDE.md의 "설정값에는 측정 결과나 명시적 근거가 붙어야 한다"를 H2에서 지키려면 Phase 3의 HikariCP 튜닝은 "측정 불가로 미적용"이라고 쓰는 수밖에 없었다. DB를 바꾸면 그 항목이 실측 가능한 과제가 된다.

**트레이드오프**
- 실행에 Docker가 필요해졌다 → `docker compose up` 한 줄로 흡수 (README 최상단)
- 테스트가 컨테이너 기동 시간만큼 느려진다 → `.withReuse(true)`로 완화
- 시드가 PostgreSQL 방언에 묶인다 (`ON CONFLICT DO NOTHING`) → 단일 DB 방침이므로 의도된 결과

**API 영향**: 없음.
**전제**: PostgreSQL 사용은 담당 교수 승인을 받았다.

**타이밍** — Phase 0 기준점 커밋 **전에** 전환했다. Phase 6의 "개선 전/후 비교"는 양쪽이 같은 DB에서 돌아야 성립하므로, 기준점을 H2로 못 박은 뒤 바꾸면 DB 교체 효과와 최적화 효과가 섞여 비교표를 쓸 수 없게 된다.

## 7. 호스트 DB 포트를 5432로 노출하지 않는다

**일반적 관행**: `ports: "5432:5432"`
**변경**: `ports: "${POSTGRES_PORT:-5433}:5432"` — 호스트는 5433, 컨테이너 내부는 5432 유지

**근거**: 개발 머신에 PostgreSQL이 이미 설치돼 있는 것은 흔한데, 이때의 충돌이 **명시적으로 실패하지 않는다.**
로컬 PostgreSQL이 `127.0.0.1`·`[::1]`만 바인딩하면 Docker는 와일드카드 `*:5432` 바인딩에 **성공**한다. 포트 충돌 에러가 나지 않고, 대신 `localhost:5432`로 가는 연결이 컨테이너가 아니라 기존 로컬 DB로 조용히 흘러간다.

증상은 원인에서 멀다 — 이번에도 애플리케이션은 `Unable to determine Dialect without JDBC metadata`로 죽었고(Hibernate 6.5.2의 NPE가 원래 SQLException을 삼킨다) 로그 어디에도 포트 얘기가 없었다. 진단 비용이 실패의 사소함에 비해 지나치게 크다.

**설계 원칙**: 실패하려면 **시끄럽게** 실패해야 한다. 조용히 잘못된 대상에 붙는 기본값은 피한다.
5433도 절대 안전하지는 않으므로 `POSTGRES_PORT`로 덮어쓸 수 있게 하고 `.env.example`과 README에 변경 방법을 안내한다.

**트레이드오프**: 표준 포트가 아니라 `psql -p 5433`처럼 포트를 명시해야 한다. 조용한 오접속을 겪는 비용보다 싸다.
**적용 범위**: 호스트 노출 포트만. 컨테이너 네트워크 내부(`docker` 프로파일)는 표준 5432를 그대로 쓴다.

## 8. 스펙이 정하지 않아 직접 정한 것들

계약을 어긴 것이 아니라 **빈칸을 채운** 항목. Phase 0에서 판단이 필요했다.

| 항목 | 결정 | 근거 |
|---|---|---|
| `Response` 필드명 | `result` / `message` / `body` | SPEC 2절은 "공통 Response로 감싼다"만 규정하고 필드명을 정하지 않았다. 성공·실패 판별 / 사유 / 페이로드의 3분할 |
| `PagedList` 필드명 | `total` / `offset` / `count` / `list` | 위와 같음 |
| `offset` 해석 ⚠️ **미확정** | 페이지 번호 (`PageRequest.of(offset, count)`) | 아래 별도 설명 |
| 주문·취소 요청 클래스 | `OrderRequest` (productId, quantity) | 엔티티로는 이 바디를 받을 수 없다 — `OrderItem`은 `Product` 참조를 갖지 `productId`를 갖지 않는다 |
| 고객 주문 조회 응답 | `OrderListDto` + `OrderItemDto` | SPEC 2절이 요구하는 평탄화된 `products` 배열은 엔티티만으로 만들 수 없다. Phase 0의 "엔티티 직접 노출"에서 벗어나지만 **계약이 강제한 예외** |
| 로그인 응답 바디 | 고객 정보 반환, 비밀번호만 제외 | 강의 자료(인쇄 549·555)가 "고객 정보 반환"이라 SPEC 2절 문구도 이에 맞춰 정정했다 |
| 비즈니스 예외의 HTTP 상태 | Phase 0은 200 + `fail` 바디 | SPEC 4절 매핑표에는 403 BOLA(Phase 2)·낙관적 락 409(Phase 3) 결과물이 섞여 있다. 즉 그 표는 **최종 목표**이지 Phase 0 산출물 명세가 아니다. 매핑은 Phase 2에서 붙인다 |

### `offset` 해석 — 확정하지 못한 항목

강의 자료(인쇄 548 `ProductService`, 550 `CustomerService`)는 **"Pageable 객체 생성"까지만 명시하고
`PageRequest.of()`에 무엇을 넣는지 제시하지 않는다.** 완성 코드는 "별도 Spring Boot 프로젝트 파일"로
배포된다고만 돼 있어(인쇄 556 각주) 확인할 수 없었다.

`Pageable`의 표준 용법인 **페이지 번호**로 해석했다. 다만 파라미터명 `offset`은 통상
**건너뛸 레코드 수**를 의미하므로, 명칭만 놓고 보면 `page`가 정확한 이름이다.

| 해석 | `offset=1&count=10`의 결과 |
|---|---|
| 페이지 번호 (현재 구현) | 101번째부터 10건 |
| 건수(행 오프셋) | 11번째부터 10건 |

건수 해석으로 바꿔야 한다면 `PageRequest.of(offset / count, count)`가 되며,
API 계약(URI·파라미터명)은 그대로이고 Service 한 줄만 고치면 된다.

**상태: 교수님 확인 대기.** E2E가 쓰는 `offset=0`에서는 두 해석의 결과가 같아 지금은 드러나지 않는다.

## 9-1. 시크릿의 기본값은 애플리케이션이 아니라 실행 환경이 준다 (Phase 2 A-2)

**Phase 0**: `application.yml`에 `jwt.secret`이 평문
**변경**: 프로파일별로 분리 — `docker`는 `${JWT_SECRET}` **필수**, `local`만 개발 전용 기본값

기본값을 둘지가 쟁점이었다. **두면 그 값이 곧 새로운 하드코딩**이고, **안 두면 `.env` 없이는
`docker compose up`이 실패해** Phase 0에서 확보한 "클론 후 한 줄 실행" 이식성이 깨진다.

**둘을 계층으로 나눠 해결했다.**

| 계층 | 정책 |
|---|---|
| 애플리케이션 (`application-docker.yml`) | `${JWT_SECRET}` — 기본값 **없음**. 없으면 기동 실패 |
| 실행 환경 (`docker-compose.yml`) | `JWT_SECRET: ${JWT_SECRET:-dev-only-...}` — 개발 편의 제공 |

애플리케이션은 **"시크릿 없이는 뜨지 않는다"** 는 계약을 지키고, 개발 편의는 실행 환경이 책임진다.
`docker compose up` 한 줄은 그대로 되고, 컨테이너 밖에서 직접 배포하면 시크릿을 빠뜨릴 수 없다.
DB 접속 정보에 이미 적용한 원칙(`docker`는 fail-fast, `local`은 기본값)과 같은 기준이다.

기본값 문자열은 `dev-only-do-not-use-in-production-0123456789`다. **값 자체에 용도를 박아 두어**
실수로 운영에 흘러가도 로그·설정 어디서든 눈에 띄게 했다.

### 키 길이가 서명 알고리즘을 결정한다 (실측)

`Keys.hmacShaKeyFor()`는 키 길이로 알고리즘을 고른다. 시크릿을 바꿀 때 길이도 함께 정해야 한다.

| 시크릿 길이 | 알고리즘 |
|---|---|
| 32바이트 미만 | **`WeakKeyException`** — 기동 실패 |
| 32~47 | HS256 |
| 48~63 | HS384 |
| 64 이상 | HS512 |

실측으로 확인했다 — 기본값(44바이트)은 `{"alg":"HS256"}`, 오버라이드값(55바이트)은 `{"alg":"HS384"}`로
**같은 코드에서 알고리즘이 달라졌다.** 시크릿 로테이션 시 길이를 바꾸면 알고리즘도 바뀌므로,
기존 토큰 검증에 영향이 있는지 확인해야 한다.

### fail-fast를 설계했는데 fail-late였다

`SessionHandler`가 요청마다 `Keys.hmacShaKeyFor()`를 호출하고 있었다. 그래서 **시크릿이 너무 짧아도
앱이 정상적으로 떴고**, `WeakKeyException`은 첫 로그인에서야 터졌다 — 그것도 500
`"internal server error"`로 나가 원인이 보이지 않았다.

키 생성을 `@PostConstruct`로 옮겨 **기동 시점에 실패**하게 했다. 부수 효과로 요청마다 키 객체를
새로 만들던 것도 사라졌다. 7절의 "실패하려면 시끄럽게 실패해야 한다"를 스스로 어기고 있었던 셈이다.

## 9-2. 쿠키 보안 플래그와 토큰 만료 (Phase 2 A-3)

**Phase 0**: 플래그 없는 평쿠키, 만료 1시간이 근거 없는 임시값
**변경**: `HttpOnly` + `SameSite=Strict` + `Path=/` 고정, `Secure`는 환경변수로 제어

`jakarta.servlet.http.Cookie`는 SameSite를 지원하지 않아 스프링의 `ResponseCookie`로 만들고
`Set-Cookie` 헤더에 직접 싣는다.

| 플래그 | 값 | 막는 것 |
|---|---|---|
| `HttpOnly` | 항상 true | XSS로 스크립트가 주입돼도 자바스크립트가 토큰을 읽지 못한다 |
| `SameSite` | `Strict` | 교차 사이트 요청에 쿠키가 실리지 않는다 (CSRF) |
| `Secure` | `${COOKIE_SECURE:false}` | HTTPS에서만 전송. 아래 참조 |
| `Path` | `/` | 전 경로에서 사용 |

### SameSite를 Strict로 둔 이유

`Lax`는 **최상위 내비게이션 GET**에 쿠키를 실어준다. 외부 링크를 타고 들어와도 로그인이 유지되므로
사용성이 좋다. 하지만 **이 API에서 인증이 필요한 요청은 전부 `POST`(`/order`·`/cancel`)와
`PUT`·`DELETE`** 다. `Lax`가 완화해주는 경로(GET)에는 애초에 인증이 필요 없으므로,
완화해서 얻을 것이 없고 CSRF 표면만 넓어진다.

> **한계** — 프론트엔드가 없어 **실제 CSRF 시나리오를 테스트하지 못했다.** 검증한 것은
> `Set-Cookie` 헤더에 `SameSite=Strict`가 실린다는 사실까지다. 브라우저가 교차 사이트 요청에서
> 실제로 쿠키를 빼는지는 브라우저 동작이므로 확인 범위 밖이다.

### Secure는 프로파일이 아니라 전송 계층이 결정한다

처음에는 DB·시크릿과 같이 **프로파일별로 나누려 했다** (`local`은 false, `docker`는 true).
구현하다 보니 축이 잘못됐다.

**`docker` 프로파일도 HTTP로 서비스한다.** 여기서 `Secure=true`로 켜면 브라우저와 Postman이
쿠키를 아예 보내지 않아 **채점 환경에서 로그인이 동작하지 않는다.** `docker` = 운영이 아니라
`docker` = 컨테이너 실행일 뿐이고, 이 프로젝트에는 TLS를 종단하는 프로파일이 없다.

`Secure`를 가르는 것은 프로파일이 아니라 **전송 계층이 HTTPS인가**다. 그래서 프로파일 분리를 걷어내고
공통 설정에 `${COOKIE_SECURE:false}`로 두었다. TLS 종단(리버스 프록시 등) 뒤에 배포하는 순간
`COOKIE_SECURE=true`로 켠다 — Phase 5에서 HA 다중 인스턴스 + 로드밸런서를 구성할 때가 그 지점이다.

**끈 사실이 조용히 넘어가지 않게 기동 로그에 정책을 찍는다.**

```
쿠키 정책 — HttpOnly=true, Secure=false, SameSite=Strict, Path=/, Max-Age=3600s
Secure=false — HTTP 환경 전용이다. TLS 뒤에 배포하면 COOKIE_SECURE=true로 켠다
```

설정 파일을 열어봐야만 알 수 있으면 운영에서 확인을 건너뛰게 된다. A-2에서 기본 시크릿 문자열에
`dev-only-do-not-use-in-production`을 박은 것과 같은 발상이다 — **위험한 기본값은 스스로를 드러내야 한다.**

### 토큰 만료 1시간 — 근거

Phase 0에서 임시값으로 표시해둔 값을 그대로 확정한다. 다만 임시가 아니라 **근거 있는 선택**으로 바꾼다.

리프레시 토큰이 없으므로 만료되면 재로그인해야 한다. 짧으면 학습·시연 중 계속 끊기고, 길면 탈취 시
노출 창이 커진다. 1시간은 그 절충이다. 값을 바꿀 근거(세션 길이 측정, 위험도 평가)가 없으므로
숫자를 흔들지 않는다.

**실무라면 구조가 다르다** — 액세스 토큰을 5~15분으로 짧게 두고 **리프레시 토큰을 분리**한다.
그러면 탈취된 액세스 토큰의 유효 기간이 짧고, 리프레시 토큰은 회전·폐기가 가능해 강제 로그아웃도 된다.
이 프로젝트에 넣지 않는 이유는 토큰 저장소(폐기 목록)와 회전 로직이 필요해 **범위가 인증 서버 수준으로
커지기 때문**이며, 그것이 이 과제의 학습 목표는 아니다.

## 9-3. 매핑 작업이 드러낸 에러 코드 설계의 결함 (Phase 2 B-1)

Phase 0~1에서는 **모든 응답이 200**이었다. 그래서 각 `Error` 코드가 어떤 상황에서 나가는지
**HTTP 레벨에서 확인된 적이 없었다.** 매핑을 붙이는 작업이 곧 전수 조사가 됐고, 두 가지가 드러났다.

### 매핑표 (SPEC.md 4절)

| Error | 상태 | 확인 |
|---|---|---|
| `DATA_NOT_FOUND` | 404 | 없는 상품 조회 → 404 |
| `DATA_DUPLICATED` | 409 | 중복 가입 → 409 |
| `INSUFFICIENT_FUNDS` | 400 | 포인트 부족 → 400 |
| `INSUFFICIENT_QUANTITY` | 400 | 취소 초과 → 400 |
| `NOT_AUTHENTICATED` | 401 | 미인증 주문 → 401 |
| `ParameterException` | 400 | 빈 상품명 → 400 |
| 예상 못한 예외 | 500 | traceId만 노출 |

상태를 `Error` enum이 직접 들고 있다. 핸들러에 `switch`를 두면 **코드를 추가할 때 매핑을 빠뜨려도
컴파일이 되고, 그 코드는 조용히 500으로 나간다.** 한자리에 두면 빠뜨릴 수 없다.

### 결함 ① 검증 실패가 404로 나가고 있었다

`Customer.changePoint`의 음수 포인트 검증이 `DATA_NOT_FOUND`를 던지고 있었다. 강의 자료가 두 검사를
한 줄에 묶어 적은 것을 Phase 0에서 그대로 따른 것이다(10절 판정 기준). 매핑하니 **검증 실패가
404로 나갔다** — 클라이언트는 "고객이 없다"로 읽는다. `ParameterException`(400)으로 교정했다.

**Phase 0에서 예고한 대로 매핑 작업이 이 부정확함을 드러냈다.** 그때 고쳤다면 이 서사가 없었다.

### 결함 ② 사용자 열거 (User Enumeration) — 새로 발견

로그인 실패가 **두 갈래**로 나가고 있었다.

| 상황 | Phase 1까지 | 공격자가 얻는 정보 |
|---|---|---|
| 없는 `customerId` | `DATA_NOT_FOUND` → 404 | **이 ID는 존재하지 않는다** |
| 틀린 비밀번호 | `NOT_AUTHENTICATED` → 401 | **이 ID는 존재한다** |

응답만 보고 **유효한 계정 목록을 만들 수 있다.** 이것이 사용자 열거(User Enumeration)이며,
OWASP가 별도 항목으로 다루는 알려진 취약점이다. 확보된 ID 목록은 크리덴셜 스터핑·표적 피싱의 입력이 된다.

**두 경우 모두 401 `NOT_AUTHENTICATED`로 통일했다.** 응답 코드만 통일하고 내부 `Error` 코드를
유지하는 방법도 검토했으나, **응답 바디에 `message: "DATA_NOT_FOUND"`가 그대로 실려 구분이 새어 나간다.**
상태만 맞춰서는 막히지 않는다.

내부 진단은 포기하지 않았다 — 로그에는 사유를 구분해 남긴다.

```
business error: NOT_AUTHENTICATED: no such customerId
business error: NOT_AUTHENTICATED: password mismatch
```

> **남은 취약점** — 없는 ID는 BCrypt 검증을 건너뛰므로 **응답이 미세하게 빠르다.** 타이밍으로
> 존재 여부를 추정할 여지가 있다. 표준 대응은 없는 ID에도 더미 해시 연산을 태우는 것이다.
> 지금 넣지 않는 이유는, **이 서비스에 요청 속도 제한이 없어** 타이밍 차이를 재기 전에 무제한 시도가
> 먼저 가능하기 때문이다. 순서상 rate limiting이 먼저다 (현재 미적용, 12절 참조).

### 검토했으나 바꾸지 않은 것 — `INSUFFICIENT_*`를 409로

`INSUFFICIENT_FUNDS`·`INSUFFICIENT_QUANTITY`는 **요청 자체는 올바르고 현재 상태와 충돌**하는 경우라
`409 Conflict`가 더 정확하다는 견해가 있다. SPEC 4절이 400으로 명시하고 있어 계약을 따랐다.

판단 근거 — 400과 409의 구분은 실무에서도 갈리고(비즈니스 규칙 위반을 400으로 두는 API가 흔하다),
**계약을 벗어날 만큼 명백한 오류가 아니다.** 반면 결함 ①②는 각각 "검증 실패를 404로 알림",
"계정 존재 여부 노출"이라 성격이 다르다. **명백한 오류는 고치고, 견해가 갈리는 것은 계약을 따른다.**

### 500 유출 차단

스택트레이스는 로그에만 남기고 응답에는 8자리 `traceId`만 내보낸다. 예외 메시지에 테이블명·쿼리·
파일 경로가 섞여 나가면 그 자체가 정보 유출이다.

```
{"result":"fail","message":"internal server error (traceId: 784b9687)","body":null}
```

`HttpMessageNotReadableException`(깨진 JSON) 핸들러도 함께 추가했다. **없으면 클라이언트 잘못이
500으로 나간다** — 실제로 겪었다. 이제 400이다.

## 9-4. Bean Validation 도입과 ParameterException의 남은 자리 (Phase 2 B-2)

### 고치기 전에 실제로 뚫리는지 확인했다

Phase 0 점검에 "`quantity` 음수 검증 없음"이 적혀 있었지만, 5단계에서 불변식을 엔티티로 옮기며
이미 막혔을 수도 있었다. **먼저 재현해봤다.**

| 시나리오 | 결과 |
|---|---|
| `quantity=-5` 주문 | 잔액 **1,000,000 → 1,075,000** (75,000 증가). DB에 `(-5, -75000.00)` |
| `quantity=0` 주문 | 의미 없는 행이 생성됨 |
| `quantity=-10` 취소 (2개 보유) | 수량 **2 → 12**로 증가, 잔액 970,000 → 820,000 |

**둘 다 뚫려 있었다.** 특히 두 번째가 더 위험하다. `refundPoint`에는 잔액 검사가 없다 —
환불은 잔액을 늘리는 연산이니 필요가 없기 때문이다. 그래서 **음수 환불은 `usePoint`의 잔액 검사를
우회해 포인트를 차감**하며, 잔액이 음수까지 갈 수 있다. "포인트는 음수가 될 수 없다"는 불변식이
**정상 경로가 아닌 곳으로 뚫려 있었다.**

### 두 계층으로 막는다

| 계층 | 무엇 | 왜 |
|---|---|---|
| 웹 진입 | `@NotNull @Positive quantity` 등 | 잘못된 요청을 도메인까지 내려보내지 않는다 |
| 도메인 | `usePoint`/`refundPoint`/`addOrder`/`cancel`의 양수 검사 | Bean Validation은 **HTTP 진입만** 지킨다. 배치·다른 Service가 부르면 통과한다 |

5단계의 "Service를 우회해도 막힌다"와 같은 원칙이다. Bean Validation은 **한 겹**이지 전부가 아니다.

### 역할 분담 — MethodArgumentNotValidException이 기본, ParameterException은 나머지

Bean Validation은 **필드 단위 선언적 검증**에 강하고, 필드 간 관계나 조회가 필요한 검증은 표현이 어렵다.
그 경계대로 갈랐다.

| 검증 | 담당 |
|---|---|
| 값이 비었는가·양수인가 (`@NotBlank`, `@NotNull`, `@Positive`) | Bean Validation |
| 조회해야 아는 것 (중복 ID, 존재 여부) | `ResponseException` (기존 그대로) |
| 나머지 | `ParameterException` |

**`ParameterException`이 던져지는 자리는 실제로 크게 줄었다.** 자료의 이 예외는
**Bean Validation 도입 전 수동 검증을 위한 것**이었고, 도입 후에는 두 경우에만 남는다.

**① 연산에 따라 필수 여부가 달라지는 필드** — `ProductRequest.id`는 등록에는 불필요하고 수정·삭제에는
필수다. 하나의 DTO에 `@NotNull`을 걸면 등록이 막힌다. Bean Validation의 *validation groups*로 표현할 수
있지만, 그룹 인터페이스를 만들고 `@Validated(Update.class)`로 갈아끼우는 비용이 조건 두 줄보다 크다.

**② 엔티티가 지키는 도메인 불변식** — `Product.of`, `Customer.register`·`changePassword`·`changePoint`,
`usePoint`/`refundPoint`/`addOrder`/`cancel`의 양수 검사. 이들은 **웹 진입과 무관하게** 지켜져야 한다.

반대로 **사라진 자리**도 기록해둔다.
- `OrderService`의 `productId`·`quantity` null 검사 → `@NotNull`이 대체
- `CustomerService.loginCustomer`의 `isAnyEmpty` → `CustomerSession`의 `@NotBlank`가 대체.
  6단계에서 "Phase 2 Bean Validation에서 Controller로 올라간다"고 예고한 항목이 실제로 올라갔다

### 응답 형식 — 자료의 형식에 맞췄다

`MethodArgumentNotValidException`은 필드별 오류를 여러 개 담지만 공통 `Response`의 `message`는 하나뿐이다.
자료가 `ParameterException("productName", "productPrice")`처럼 **필드명을 나열**하는 형식이었으므로 그대로 따랐다.

```
POST /api/products {"productName":"","productPrice":-1}
→ 400 {"message":"invalid parameter: productName, productPrice"}
```

필드명을 **정렬**한다. 검증 순서가 보장되지 않아 같은 요청에 메시지가 달라지면 클라이언트가 비교할 수 없다.

### `@Valid`를 삭제 경로에 걸지 않는 이유

`CustomerRequest`는 가입(둘 다 필요)과 탈퇴(`customerId`만)에서 함께 쓰인다. `ProductRequest`도
등록·수정(이름·가격 필요)과 삭제(`id`만)에서 함께 쓰인다. 삭제에 `@Valid`를 걸면 **보내지 않아도 되는
필드를 요구**하게 된다. 그래서 `@Valid`를 메서드별로 선택 적용했다 — 위 ①과 같은 뿌리의 문제다.

## 9-5. BOLA 방어와 인증 없이 열려 있던 조회 (Phase 2 B-3)

**BOLA**(Broken Object Level Authorization) — OWASP API Security Top 10 **#1**.
인증만으로는 부족하다. 로그인한 사용자가 **남의 식별자**를 요청에 넣으면 그대로 통했다.

### 403 코드 이름을 `NOT_OWNER`로 정한 이유

SPEC 4절이 "(본인 불일치) 403"으로 이름 없이 비워둔 자리다.

`NOT_AUTHORIZED`가 무난하지만 쓰지 않았다. **`NOT_AUTHENTICATED`와 철자가 두 글자 차이라
코드에서 눈으로 구별되지 않는다.** 401과 403을 뒤바꿔 쓰는 실수가 정확히 그 혼동에서 나온다.
`NOT_OWNER`는 무엇이 문제인지를 직접 말한다 — **요청 대상이 본인 소유가 아니다.**

| 코드 | 상태 | 뜻 |
|---|---|---|
| `NOT_AUTHENTICATED` | 401 | **누구인지** 확인되지 않았다 |
| `NOT_OWNER` | 403 | 누구인지는 알지만 **그 대상에 권한이 없다** |

역할(admin 등) 기반 인가가 생기면 그때 별도 코드를 추가한다. 지금 있는 유일한 403 사유는 소유권이다.

### 소유권 검사를 존재 확인보다 먼저 한다

```java
requireOwner(loginCustomerId, request.getCustomerId());   // 먼저
Customer customer = findCustomer(request.getCustomerId()); // 나중
```

순서를 바꾸면 **남의 계정에 대해 404(없음)와 403(있지만 권한 없음)이 갈려 계정 존재 여부가 노출된다.**
9-3절의 사용자 열거와 같은 형태다. 실측으로 확인했다 — 존재하는 계정과 없는 계정 모두 403이다.

### 인증 없이 열려 있던 조회 두 개 — 하나는 고치고 하나는 남겼다

자료는 `GET /api/customers/{customerId}`와 `GET /api/customers/list`를 **인증 불필요**로 두었다.
9-3절의 기준("명백한 오류는 고치고, 견해가 갈리는 것은 계약을 따른다")을 적용하되,
**"고친다"는 선택지가 실제로 존재하는가**를 함께 따졌다.

| 엔드포인트 | 노출되는 것 | 범위 안의 완전한 해법이 있는가 | 결정 |
|---|---|---|---|
| `GET /{customerId}` | 특정 고객의 주문 이력·잔액 | **있다** — 본인만 조회(BOLA 방어). 역할 개념이 필요 없다 | **고쳤다** |
| `GET /list` | 전체 고객 ID + 잔액 | **없다** — 올바른 해법은 관리자 역할 기반 접근 제어다 | 계약 유지, 한계 기록 |

`GET /{customerId}`를 고친 근거는 **선례**다. SPEC 1절은 이미 `PUT`/`DELETE`에 자료에 없는 인증 요구를
BOLA 방어로 추가해 두었다. 같은 성격의 개인정보 노출이므로 같은 처리를 한다. SPEC.md 1절 표와 주석도
실제 동작에 맞춰 갱신했다 — **문서가 코드와 다르면 그 자체가 결함이다.**

`GET /list`를 고치지 않은 근거는 **"인증만 요구"가 방어가 되지 못하기 때문**이다. 가입이 자유로우므로
공격자는 계정 하나 만들고 그대로 전체 목록을 얻는다. 익명 스크래핑은 막지만 열거는 못 막는
**반쪽 조치를 위해 계약을 바꾸는 것**은 이득보다 비용이 크다.

> **이 결정이 9-3절의 성과를 제한한다 — 함께 읽어야 한다.**
> B-1에서 로그인 응답을 401로 통일해 사용자 열거를 막았지만, **`GET /list` 한 번이면 전체 `customerId`를
> 그대로 얻는다.** 실측 확인했다. 로그인 벡터는 닫혔고 목록 벡터는 계약상 열려 있다.
> "사용자 열거를 막았다"고 단독으로 주장하면 과장이다. 완전한 차단은 역할 기반 접근 제어가 전제다.

## 9-6. 삭제 시 참조 무결성 — 두 케이스를 나눠 판단했다 (Phase 2 B-4·B-5)

주문이 있는 상품·고객을 삭제하면 FK 제약에 걸려 **500**이 났다. 세 방식을 놓고 판단했다.

| 방식 | 검토 결과 |
|---|---|
| **거부** (`DATA_IN_USE` 409) | **채택.** 범위가 작고 정책이 명확하다 |
| Soft Delete | **기각.** 조회 로직 전반에 조건이 붙고, **`(customer_id, product_id)` 복합 UNIQUE와 충돌한다** — 삭제 표시된 행이 남아 있으면 같은 조합을 다시 만들 수 없다. 취소 후 재주문이 막힌다 |
| Cascade | 아래 참조 |

### 상품 삭제 — 거부

"주문 이력이 있는 상품은 삭제할 수 없다"는 실무에서 흔한 정책이다. 상품을 지우면 그 상품을 산
주문 기록이 무엇을 가리키는지 알 수 없게 된다.

### 고객 탈퇴 — 함께 삭제가 아니라 거부. 이유가 다르다

"본인이 나가겠다는데 막는 게 이상하지 않은가"를 따로 검토했다. **이 구조에서는 함께 삭제가 고객에게 손해다.**

`OrderItem`은 "주문 이력"이 아니라 **"현재 보유 수량"** 이고(13절), 포인트는 **취소해야 환불된다.**
탈퇴 시 자동 삭제하면 **환불 없이 보유 상품만 사라진다.** 먼저 취소하게 하면 포인트를 돌려받고 나간다.

실측한 흐름이 이를 보여준다.

```
보유 2개 상태 → 탈퇴 시도        409 DATA_IN_USE
취소                              잔액 1,000,000 복귀 (환불)
탈퇴                              200
```

구현상으로도 함께 삭제는 문제가 있다. `CustomerService`가 주문을 지우려면 **customer → order 의존**이
필요한데 `order → customer`가 이미 있어 **순환**이 된다(4절). 우회하려면 상위 조율 계층이나 도메인
이벤트가 필요하고, 연산 하나를 위해 계층을 늘리는 것은 과하다.

> **함께 삭제가 필요해지면** 도메인 이벤트가 정답이다 — `customer`가 `CustomerDeleted`를 발행하고
> `order`가 구독한다. 의존 방향을 뒤집지 않고 반응할 수 있다. 이것은 **MSA 전환 시 필요한 메커니즘과
> 같다**(Saga, `PLAN.md` Phase 7). 지금 넣지 않는 이유는 단일 프로세스에서 이벤트 인프라를 들이는 비용이
> 얻는 것보다 크기 때문이다.

### FK 위반을 번역한다 — 도메인 경계를 지키면서

상품 삭제 전에 "이 상품을 주문한 고객이 있는가"를 확인하려면 `product`가 `order`의 Repository를
봐야 하는데, 그러면 **순환이 된다.**

**참조 무결성의 authority는 DB다.** 그래서 미리 묻지 않고, DB가 거부한 것(`DataIntegrityViolationException`)을
`DATA_IN_USE`로 번역한다. 경계를 지키면서 정확한 응답을 낸다.

한 가지 함정이 있었다 — `delete()` 뒤에 **`flush()`를 명시**해야 한다. 없으면 FK 위반이 트랜잭션 커밋
시점에 터져 `try` 블록 밖으로 나가고, 번역되지 못한 채 500이 된다.

### `DATA_IN_USE`가 409인 이유

요청 자체는 올바르고 **현재 상태와 충돌**하는 경우다. `INSUFFICIENT_*`는 SPEC 4절이 400으로 명시해
계약을 따랐지만(9-3절), 이 코드는 **자료에 없어 상태 충돌 의미대로 정할 수 있었다.**

### `@JsonIgnore` 이중 방어 (B-4)

응답 DTO 분리로 비밀번호는 이미 정상 경로에서 노출되지 않는다. `Customer.customerPassword`의
`@JsonIgnore`는 **엔티티가 실수로 직렬화되는 경로**를 막는 두 번째 겹이다 — 누군가 Controller에서
엔티티를 그대로 반환하거나, 디버깅용으로 JSON을 로그에 찍을 때.

> **이 방어는 E2E로 확인할 수 없다.** 현재 엔티티가 직렬화되는 경로가 없기 때문이다.
> **테스트할 수 없는 방어는 값이 확인되지 않은 방어**이므로, Phase 4에서 엔티티 직렬화 단위 테스트로
> 고정한다 (`ObjectMapper`로 `Customer`를 직렬화해 `customerPassword` 키가 없음을 단언).

## 10. Phase 0에서 자료를 따를지 판단하는 기준

개별 항목의 근거만 쌓이면 케이스마다 판단이 흔들린다. 판정 가능한 기준을 먼저 둔다.

> **Phase 0의 역할은 자료를 문자 그대로 복사하는 것이 아니라, 이후 Phase가 개선할 대상을 보존하는 것이다.**

판정 질문은 하나다 — **"이걸 지금 고치면 어느 Phase의 할 일이 사라지는가?"**

| 답 | 판단 |
|---|---|
| 사라지는 Phase가 **있다** | **자료를 따른다.** 그 결함이 곧 개선 전 상태다. 미리 고치면 개선 전/후 비교가 성립하지 않고 보고서의 근거가 사라진다 |
| 사라지는 Phase가 **없다** | 따르지 않아도 된다. 특히 따르는 것이 **기준점을 오염시킨다면** 따르지 않는다 |

"의미론적으로 더 낫다", "설계가 더 깔끔하다"는 그 자체로는 근거가 되지 못한다. 그것들은 Phase 1~3의 몫이다.

### 적용 결과

| 항목 | 이후 Phase의 개선 대상인가 | 판단 |
|---|---|---|
| Service가 `Response`를 반환 | **Phase 1** — 인증 분리와 함께 웹 응답 포맷을 Service에서 걷어낸다 | 자료를 따른다 |
| 음수 `customerPoint`에 `DATA_NOT_FOUND` | **Phase 2** — "Error → HTTP 상태 매핑". 검증 실패가 404로 나가는 것이 그 작업에서 드러날 부정확함이다 | 자료를 따른다 |
| 신규 Product ID `0L` 세팅 | 아니다. Phase 3 성능 과제는 N+1·락·캐시이지 이 항목이 아니다 | 따르지 않는다 |
| 자료의 명백한 오기 5건 (11.1) | 아니다. 애초에 따를 수 없다 | 따르지 않는다 |

`0L`이 이 기준에서 **반대 결론**에 도달하는 것이 중요하다. 쿼리 2회 → 3회라는 효율 문제로만 보면 사소하지만,
따를 경우 **기준점의 성능이 인위적으로 나빠져 Phase 6의 개선 전/후 비교가 왜곡된다.** 개선 대상이 아닌데
기준점만 오염시키는 항목이므로 따르지 않는 것이 정당하다.

### 왜 "일관성"을 기준으로 쓰지 않는가

"일관성"은 사후에 *"그때 왜 달랐는가"* 를 설명하는 말이라 **앞으로 나올 케이스를 판정하지 못한다.**
기준은 판정 가능해야 한다.

기준을 세운 뒤에는 **기존 결정과 충돌하는지 확인한다.** 예를 들어 "외부에 보이는 동작은 의미론을 우선한다"는
대안 기준을 검토했으나, 그것을 채택하면 *비즈니스 예외가 전부 HTTP 200인 것*도 지금 고쳐야 해
Phase 2 항목으로 남기기로 한 결정과 자기모순이 된다. 그래서 탈락시켰다.

## 11. 강의 자료의 오류와 해석

원본 자료라고 무비판 수용하지 않는다. 대조 과정에서 나온 오기·모순과 그 판단을 남긴다.

### 11.1 명백한 오기 — 따르지 않음

| 위치 | 자료 내용 | 판단 |
|---|---|---|
| 인쇄 546 | 실습 2-3 슬라이드 제목은 `[CustomerProductRepository.java]`인데 내용은 "**OrderItem** 엔터티를 관리하기 위해" | 폴더 구조(인쇄 556)와 `CustomerService` 필드가 모두 `OrderItemRepository`다. **3곳 중 2곳**을 따라 `OrderItemRepository`로 구현 |
| 인쇄 548 | `[ProductService.java]` 슬라이드인데 클래스 선언이 `public class CustomerService` | 다음 슬라이드에서 복사한 실수. `ProductService`로 구현 |
| 인쇄 549 | `deleteProduct` 설명에 "**저장** 후 Response 반환" | 삭제 메서드에 저장이 있을 수 없다. 삭제 후 반환 |
| 인쇄 551 | `deleteCustomer`도 동일하게 "저장 후 Response 반환" | 위와 같음 |
| 인쇄 551 | `createCustomer(Customer customerSession)` — 타입은 `Customer`인데 파라미터명이 `customerSession` | 로그인용 `CustomerSession`과 혼동한 흔적. 파라미터명은 `customer` |

### 11.2 따르지 않기로 한 지침 — 신규 Product의 ID를 `0L`로 세팅 (인쇄 549)

**구현하지 않는다.** 추측이 아니라 SQL 로그로 확인했다 → [`docs/evidence/product-id-0L-vs-null.md`](evidence/product-id-0L-vs-null.md)

`Product.id`는 `Long` 래퍼 + `@GeneratedValue(IDENTITY)`다. Spring Data의 `isNew()`는 래퍼 타입에서 `id == null`로 판정하므로, `0L`을 넣으면 non-null이라 **"이미 있는 엔티티"로 분류되어 `persist` 대신 `merge` 경로를 탄다.** merge는 id=0인 행을 찾으러 SELECT를 날리고, 없으면 결국 INSERT한다.

측정 결과 **상품 등록 1건당 쿼리 2회 → 3회**. 결과는 같고 SELECT만 늘어난다.
이 지침은 id가 원시형 `long`이던 시절(기본값 0이라 null 판정이 불가능했던) 관용구로 보인다.

### 11.3 해석으로 메운 부분

- **`updateCustomer`의 포인트 검증 오류 코드 — 자료대로 두고 Phase 2에서 교정한다.**
  자료는 "customerId와 customerPoint 유효성 체크 : 오류시 `ResponseException(Error.DATA_NOT_FOUND)`"라고 두 검사를 한 줄에 묶었다. 검증 실패에 `DATA_NOT_FOUND`("데이터를 찾을 수 없음")를 쓰는 것은 의미가 맞지 않고, Phase 2에서 매핑하면 **400이어야 할 응답이 404로 나간다.**
  한때 `ParameterException`으로 나눠 구현했다가 되돌렸다 — **그 부정확함 자체가 Phase 2 "Error → HTTP 상태 매핑"의 개선 대상**이기 때문이다. 미리 고치면 Phase 2는 매핑만 붙이는 작업이 되고, "자료의 에러 코드 설계가 부정확했고 매핑 과정에서 드러나 바로잡았다"는 근거가 사라진다 (10절 판정 기준).
  대신 맥락 메시지 `"invalid customerPoint"`를 붙여 **로그에서는 이 불일치가 보이게** 해뒀다
- **`ResponseException`의 맥락 메시지** — 자료의 `("Customer not found")`를 받도록 2-인자 생성자를 뒀다. 다만 **응답 바디에는 `Error` 코드만 내보내고 메시지는 로그에만** 남긴다. 내부 사정을 클라이언트에 흘리지 않기 위해서다
- **Service가 `Response`를 반환하는 것** — Phase 0에서는 자료를 따랐다. 계층 분리 관점에서는 Service가 웹 응답 포맷을 아는 것이 바람직하지 않지만, 개선 전 기준점이므로 보존했다. **Phase 1 6단계에서 인증 분리(`@LoginCustomer`)와 함께 걷어냈다 — 개선 완료** (5절)

## 12. 적용하지 않은 패턴과 이유

*(보고서 핵심 섹션 — 맥락 없는 기술 적용을 피했다는 근거)*

| 패턴 | 미적용 사유 |
|---|---|
| 서킷브레이커 · 벌크헤드 | 존재 목적은 **여러 외부 의존성 사이의 장애 격리**인데, 이 서비스의 외부 호출은 DB 하나뿐이다. 격리할 다른 대상이 없으므로 벌크헤드가 나눌 경계가 없고, DB가 죽으면 어차피 모든 요청이 실패하므로 서킷을 열어 얻을 것도 없다. DB 장애는 서킷브레이커가 아니라 커넥션 풀 타임아웃·획득 대기 상한으로 다루는 것이 정석이며, HikariCP 풀 크기·타임아웃 튜닝으로 자원 격리 개념을 실증한다 (PostgreSQL 전환으로 측정 가능해졌다 — 6절) |
| CDN | 순수 REST API로 정적 자원이 없다. 캐싱이라는 동일 목적은 `@Cacheable`과 HTTP 캐시 헤더로 달성 |
| MyBatis 혼용 | 실무에서 JPA와 MyBatis를 함께 쓰는 것은 흔하며, 그 근거는 명확하다 — 단순 CRUD는 영속성 컨텍스트·더티체킹으로 생산성이 높은 JPA가, 복잡한 집계·다중 조인·동적 조건·튜닝된 SQL은 MyBatis가 유리하다. 다만 **본 프로젝트의 API는 전부 단순 CRUD로, MyBatis가 우위를 갖는 쿼리가 존재하지 않는다.** 기존 CRUD를 XML로 옮기는 것은 기술을 목적 없이 추가하는 것이므로 도입하지 않았다. 도입 조건이 충족되는 시점: GROUP BY·HAVING을 동반한 통계성 조회, 조건 조합이 많은 동적 검색, 대량 배치 |
| `@ManyToMany` | 연결 테이블에 `quantity`, `orderedPrice` 같은 속성이 있어 표현 불가. `OrderItem`을 독립 엔티티로 승격 |
| Service 인터페이스 분리 | 구현체가 하나뿐인 인터페이스는 과설계. 단, 도메인 간 호출부는 MSA 분리 시 Client 교체를 위해 예외 |

## 13. 알려진 한계

- **주문 이력 부재**: 현재 `OrderItem`은 "주문 이력"이 아니라 "현재 보유 수량"에 가깝다. 취소하면 기록이 사라져 감사 추적이 불가능하다. 실무라면 `Order`(헤더) + `OrderLine`(상세) 구조로 분리해야 한다
- **offset 페이징**: 뒤 페이지일수록 느려지고, 조회 중 데이터 변경 시 항목이 중복·누락된다. 대용량에서는 커서 기반 페이징 필요
- **성능 수치의 해석**: 개발 노트북의 Docker 컨테이너 기준이다. 운영과 같은 DB 엔진을 쓰므로 병목의 **성격**(락 대기, 커넥션 획득 대기, 인덱스 미스)은 유효하지만, 절대 수치는 하드웨어·컨테이너 자원 할당에 좌우된다. 개선 전후를 **같은 머신·같은 컨테이너 설정**에서 측정한 상대 비교로 서술한다
- **단일 DB 인스턴스**: 복제·페일오버를 구성하지 않았다. DB가 죽으면 서비스 전체가 멈춘다. 실무라면 read replica와 자동 페일오버가 필요하다
- **`jwt.secret`이 커밋 히스토리에 남아 있다** — **현재 코드와 히스토리를 구분해 읽어야 한다.**

  | | 상태 |
  |---|---|
  | 현재 코드 | **제거됨** (Phase 2 A-2). `application.yml`에 시크릿이 없고, `docker` 프로파일은 `${JWT_SECRET}` 필수, `local`만 개발 전용 기본값을 둔다 |
  | 커밋 히스토리 | **남아 있음.** Phase 0 커밋(`449b74f`)부터 A-2 직전까지의 `application.yml`에 평문으로 들어 있다 |

  **파일에서 지우는 것은 유출을 되돌리지 못한다.** `git show 449b74f:src/main/resources/application.yml`이면 그대로 보인다.
  학습용 더미 값이고 이 저장소가 Phase 0·1 기준점 태그를 보존해야 하므로 **히스토리 재작성(`filter-repo`) 대신 문서화로 갈음한다.**
  히스토리를 다시 쓰면 `phase0-baseline`·`phase1-structure` 태그가 가리키는 커밋이 바뀌어 Phase 3·6의 비교 기준이 무너진다.

  실무라면 순서가 반대다: ① 즉시 시크릿 로테이션(유출된 값 무효화) → ② 히스토리 정리 → ③ 재발 방지(`git-secrets`·pre-commit 훅).
  지금 하지 않는 이유는 "괜찮아서"가 아니라 **"값이 가짜이고, 히스토리 보존이 이 프로젝트의 목적 중 하나라서"** 다.

## 14. 동시성 제어 방식과 충돌 이후 (Phase 3)

### 무엇을

`Customer`에 **`@Version` 낙관적 락**을 걸고, 충돌은 **409 `CONCURRENT_MODIFICATION`** 으로 응답한다.
서버가 자동 재시도(`@Retryable`)하지는 않는다.

### 왜 — 락이 없을 때 실제로 무슨 일이 일어났는가

동시 주문 100건(각 다른 상품, 단가 1,000)을 돌린 결과다 (`docs/evidence/lost-update.md`).

```
성공 100/100 · 예외 0건
최종 포인트 988,000 / 기대 900,000 — 차감 88건이 증발했다
```

**고객은 상품 100개를 받고 12개 값만 냈다.** 예외가 한 건도 나지 않았다는 점이 중요하다 —
애플리케이션은 100건 전부 성공으로 보고하므로 **로그를 아무리 뒤져도 발견되지 않는다.**

`Customer.usePoint`가 잔액을 스스로 검사하지만, 그 검사는 **자기가 읽은 값**에 대한 것이다.
불변식을 엔티티에 넣는 것과 동시 수정을 막는 것은 **다른 문제**이고, 후자는 DB가 판단해야 한다.
Phase 1에서 "불변식은 그 데이터를 가진 객체가 지킨다"를 적용했지만 그것으로는 부족했다.

### 왜 낙관적인가 — 비관적 락과 수치로 비교했다

같은 시나리오를 락 방식만 바꿔 돌렸다 (`docs/evidence/lock-comparison.md`).

| 방식 | 성공 | 실패 | 소요 | 100건 완료 시간 |
|---|---|---|---|---|
| 낙관적 (재시도 없음) | 13~14 | 86~87 | 43~47ms | — (완료 못 함) |
| 낙관적 + 재시도 | 100 | 0 | 574~586ms | 574~586ms |
| 비관적 `FOR UPDATE` | 100 | 0 | 413~426ms | **413~426ms** |

**이 시나리오에서는 비관적 락이 약 1.4배 빠르다.** 그런데도 낙관적을 택했다.

이 실험은 **한 명의 고객이 100건을 동시에 주문**한다 — 경합이 극단적으로 높은 쪽이다.
실제 트래픽에서는 서로 다른 고객이 각자의 행을 갱신하므로 **한 행에 대한 경합이 드물다.**
드문 충돌에 비관적 락을 걸면 매 주문마다 행 잠금·대기 비용을 내면서 이득은 없다.
비관적 락은 잠금 순서에 따른 **데드락** 위험이 있고, 느린 트랜잭션 하나가 그 행 전체를 막는다.

> **재고가 생기면 결론이 바뀐다.** 인기 상품 한 행에 주문이 몰리는 형태가 되어
> 이 실험의 경합 조건에 가까워진다. 그때는 비관적 락 또는 원자적 UPDATE를 재검토한다.

### `@Version`을 `Customer`에만 붙인 이유

`Product`에는 붙이지 않았다. **재고 개념이 없어 주문이 상품 행을 갱신하지 않는다** —
동시에 바뀌는 필드가 없으므로 버전을 둘 이유가 없다.
근거 없이 모든 엔티티에 붙이면 충돌하지 않을 곳에서 실패율만 올린다.

`OrderItem`도 붙이지 않았다. 같은 `(고객, 상품)` 조합에 대한 동시 주문은 복합 UNIQUE 제약이
먼저 막고, 그 경합은 고객 행 경합에 포함된다.

> **[정정 — Phase 6 부하 측정 후] 위 문장의 뒷부분이 틀렸다.**
>
> | 서술 | 판정 |
> |---|---|
> | "복합 UNIQUE 제약이 먼저 막는다" | ✅ 맞다. 실제로 제약이 막았다 |
> | **"그 경합은 고객 행 경합에 포함된다"** | ❌ **틀렸다.** 별개의 경합이고, `Customer`의 `@Version`은 관여하지 못한다 |
> | 결론("`OrderItem`에 `@Version`을 붙이지 않는다") | ✅ 유지. 다만 **이유가 다르다** — 아래 참조 |
>
> 제약이 막기는 했으나 **그 결과가 500으로 나가고 있었다.** "포함된다"고 적은 탓에
> *제약 위반이 애플리케이션 예외로 어떻게 나타나는지*를 아무도 확인하지 않았다.
> 결론이 우연히 맞았기 때문에 **틀린 근거가 세 Phase 동안 검토되지 않았다.**
>
> `OrderItem`에 `@Version`을 붙이지 않는 진짜 이유는 **붙여도 이 경합을 막지 못하기 때문**이다.
> 낙관적 락은 이미 존재하는 행의 동시 수정을 막는 장치이고, 여기서 충돌하는 것은
> **아직 존재하지 않는 행을 양쪽이 만들려는 상황**이다. 해법은 락이 아니라 예외 매핑이었다.
> 상세는 **24절**.

### 충돌 이후를 설계한다 — 왜 500이 아니라 409인가

핸들러가 없으면 `OptimisticLockingFailureException`이 일반 예외 핸들러로 떨어져
**정상적인 동시성 제어가 500으로 나간다.** 500은 "서버가 잘못했다"는 뜻이라
클라이언트는 재시도해도 되는지 알 수 없다.

409는 **"요청은 올바르고 현재 상태와 충돌한다. 다시 시도하면 성공할 수 있다"** 를 말한다.
`DATA_IN_USE`(9-6절)와 같은 부류다. 충돌 로그는 `error`가 아니라 `debug`로 남긴다 —
충돌은 정상 동작이고, 500으로 새는 쪽이 진짜 문제다.

### 자동 재시도(`@Retryable`)를 넣지 않은 이유

실험에서 재시도를 붙이면 100건이 전부 성공한다. 그런데도 서버에 넣지 않았다.

- **재시도는 부하를 키운다.** 충돌률이 높을수록 재시도가 늘고, 늘어난 재시도가 다시 충돌을 만든다.
  상한과 백오프 없이 넣으면 경합 구간에서 스스로 증폭한다
- **주문은 금전 거래다.** 서버가 조용히 재시도하면 클라이언트는 몇 번 시도됐는지 모른다.
  네트워크 타임아웃과 겹치면 중복 주문으로 보이는 상황을 만들 수 있다
- **재시도 정책은 측정 위에서 정해야 한다.** 상한·백오프 간격은 실제 충돌 분포를 봐야 정할 수 있고,
  그 측정은 Phase 6(k6 부하)의 몫이다. 지금 넣으면 근거 없는 숫자가 된다

지금은 **409로 알리고 재시도 여부를 클라이언트에 맡긴다.** 실험 코드에는 재시도가 있으나
상한(50회)을 두었고 테스트 소스에만 있다.

## 15. 규칙을 문서가 아니라 테스트로 강제한다 (Phase 4)

### 무엇을

`CLAUDE.md` 절대 규칙과 `.claude/rules/layering.md`를 **ArchUnit 규칙 12개**로 옮겼다.

### 왜 — 성실함은 이미 두 번 실패했다

| # | 무엇을 써뒀나 | 무엇을 했나 |
|---|---|---|
| 1 | `DECISIONS.md` 7절 "실패하려면 시끄럽게 실패해야 한다" | 다음 Phase에서 fail-late 코드를 짰다 (짧은 시크릿에도 앱이 정상 기동) |
| 2 | 검증 스크립트 헤더에 브레이스 확장 경고 | 같은 실수를 반복했다 |

**2번에서 실제로 막아준 것은 문서가 아니라 `chk`의 인자 수 검사 코드였다.**
경고문은 내가 직접 쓴 것이고 파일 맨 위에 있었는데도 소용이 없었다.

규칙은 지키자고 다짐하는 것이 아니라 **어길 수 없게 만드는 것**이다.
`CLAUDE.md`의 절대 규칙은 Phase 3까지 **현재 성실함에만 기대고 있었다.**

### 즉시 나온 성과 — 문서가 사실이 아니었다

순환 검사가 **실제 위반**을 찾았다.

```
customer.controller.CustomerController → order.service.OrderService
order.service.OrderService             → customer.service.CustomerService
```

`DECISIONS.md` 4절은 "의존은 order → customer, order → product **단방향**"이라고 적고 있었다.
**세 Phase 동안 사람은 못 봤다.** Service·엔티티 계층은 처음부터 깨끗했고 웹 계층에서만 새고 있었다.

원인은 `CustomerController`가 주문 엔드포인트 3종(`/{customerId}` 조회, `/order`, `/cancel`)을
서빙한 것이다. **URI 접두사가 `/api/customers`라는 이유로 그 코드를 customer 패키지에 두었는데,
URI 접두사와 소유 도메인은 별개다.**

조치 — `order/controller/OrderController` 신설. **URI·메서드·응답 형식은 그대로 유지**했다
(SPEC.md가 고정한 계약). MSA로 나눌 때도 이 배치가 맞다: `/api/customers/order`를 서빙하는 것은
고객 서비스가 아니라 주문 서비스다.

### 역검증

각 규칙을 **일부러 위반하는 코드를 넣어** 테스트가 실제로 실패하는지 확인했다 — 10건 전부 잡혔다.
통과만 보고 넘어가면 규칙이 강제되는지 알 수 없다.

## 16. 커버리지는 판단 기준과 함께만 쓴다 (Phase 4)

### 무엇을

JaCoCo 게이트를 **라인 85% / 분기 80%** 로 걸었다 (측정값 89.4% / 87.2%).
`check` 태스크에 물려 `./gradlew build`가 게이트를 지나가게 했다 —
리포트만 만들고 아무도 보지 않으면 게이트가 아니다.

### 제외한 것과 사유

| 제외 | 사유 |
|---|---|
| `ShopApiApplication` | `main()` 한 줄. 검증할 분기가 없다 |
| `global/config/**` | `@Bean` 정의를 테스트하는 것은 스프링을 테스트하는 것이다. 실제 동작은 E2E·`@WebMvcTest`가 검증한다 |
| `**/dto/**` | Lombok 생성분을 빼면 남는 것이 거의 없다. 필드 존재 여부(비밀번호 미노출 등)는 Controller 테스트가 JSON으로 단언한다 |
| Lombok 생성 메서드 | `lombok.config`의 `addLombokGeneratedAnnotation`. **클래스 단위 제외보다 정밀하다** — 같은 클래스 안의 '사람이 쓴 코드'는 그대로 집계된다 |

### 임계치의 근거

**목표치가 아니라 바닥이다.** 실측보다 낮게 잡아 정상적인 리팩터링이 게이트에 걸리지 않게 하되,
검증 없는 코드가 새로 들어오면 걸리게 한다. 실측(89.4)에 맞춰 89%로 잡으면
리팩터링 한 번에 게이트가 깨져 **임계치를 낮추는 습관**이 생긴다.

숫자 자체에 이론적 근거는 없다 — 이 프로젝트 규모에서 관측된 값에서 여유를 뺀 것이다.
**근거를 못 대는 부분은 못 댄다고 적는다.** 100%를 목표로 하지 않는 이유는 `.claude/rules/testing.md`.

### ★ 커버리지가 가리고 있던 것

계층 테스트를 다 짠 시점에 `SessionHandler`의 라인 커버리지는 **93%** 였다. 잘 덮인 클래스로 보인다.

그런데 **"서명 검증에 실패해도 페이로드의 `sub`를 그대로 신뢰한다"** 는 변이를 넣었더니
**테스트 104건 중 단 하나도 실패하지 않았다.** 위조 토큰으로 남의 계정에 접근할 수 있는
회귀가 그대로 통과한다.

원인은 다른 테스트들이 전부 **정상 토큰으로 로그인해 그 쿠키를 다시 쓰는 경로**만 밟았기 때문이다.
그 경로에서는 서명이 항상 유효하므로 `catch (JwtException)` 블록에 **들어갈 일이 없고,
들어가지 않는 코드는 어떻게 고쳐놔도 아무도 모른다.** 93%라는 숫자는 그 사실을 가린다.

> **커버리지는 "이 줄이 실행됐다"만 말한다. "이 줄이 옳은지 확인됐다"고는 말하지 않는다.**
> 단언 없는 테스트도 라인을 밟으면 숫자가 오른다.

`SessionHandlerTest` 8건을 추가해 막았다 — 다른 키로 서명한 토큰, 페이로드만 바꾼 토큰,
만료 토큰, 쓰레기 값, 쿠키 없음, 보안 플래그, 약한 시크릿 fail-fast.
같은 변이를 다시 넣으니 이번엔 3건이 잡았다.

### 그래서 커버리지를 어떻게 쓰는가

- **숫자를 올리는 도구가 아니라 "안 밟힌 곳"을 찾는 도구로 쓴다.** 위 구멍도 표를 훑다가
  "93%인데 예외 경로가 테스트에 안 보인다"에서 시작했다
- **높은 커버리지는 검증을 보장하지 않는다.** 확신이 필요한 곳은 변이를 넣어 확인한다
- Phase 4의 모든 테스트는 **역검증을 거쳤다** — 도메인 9건, 계층 12건, 아키텍처 10건,
  커버리지 게이트 1건. 실패할 수 없는 테스트는 없는 테스트보다 나쁘다

### [정정 — 전수 조사 후] 문제는 도구가 아니라 집계 단위였다

위 서술은 "커버리지의 한계"로 읽히지만, **Phase 5 착수 전 예외·실패 분기를 전수 조사한 결과
그 결론은 절반만 맞았다.**

`SessionHandler`를 "93%"로 본 것은 **클래스 단위 백분율**이다. 같은 JaCoCo 리포트를
**라인·분기 단위**로 열면 도구는 이미 정확히 말하고 있었다 —
`catch (JwtException)` 블록은 `mi > 0`(미실행)으로 찍혀 있었다.

전수 조사에서 나온 **미검증 3건이 전부 "라인 단위로는 미실행"으로 표시된 곳**이었다.

| 구멍 | 클래스 백분율 | 라인 단위 |
|---|---|---|
| 500 응답 정보 유출 | `GlobalExceptionHandler` 74% | 101~104 **미실행** |
| `ParameterException` → 400 | 같은 클래스 74% | 42~43 **미실행** |
| `supportsParameter` 타입 검사 | `LoginCustomerArgumentResolver` 100% | 25 **미실행**, 분기 1/2 |

세 번째가 특히 분명하다 — **라인 커버리지 100%인데 분기는 1/2**다. 백분율 하나로 뭉개면
"완벽히 덮인 클래스"가 되고, 분기 열을 보면 절반이 비어 있다.

**정정된 결론:**
- 커버리지는 **"실행됐다"만 말한다**는 것은 그대로 맞다 (단언 없는 테스트도 라인을 밟는다)
- 그러나 **"밟히지 않은 곳"에 대해서는 도구가 이미 정확하다.** 우리가 안 봤을 뿐이다
- **클래스 단위 백분율을 보지 말고 미실행 라인·부분 분기 목록을 본다.**
  85%라는 게이트는 회귀 방지용 바닥이고, **읽어야 할 것은 그 숫자가 아니라 목록**이다

> 변이 테스트는 여전히 필요하다 — "밟혔는데 단언이 없는" 경우는 커버리지로 알 수 없다.
> 다만 그건 **훨씬 좁은 범위**이고, 먼저 미실행 목록을 비우면 변이를 돌릴 곳도 줄어든다.

## 17. 테스트 계층 배치와 curl E2E와의 역할 분담 (Phase 4)

### 계층별 배치

| 대상 | 방식 | 건수 | 실행 시간 |
|---|---|---|---|
| 도메인 로직 | 순수 JUnit (Spring 없음) | 32 | 0.27초 |
| Service | Mockito | 23 | < 0.1초 |
| Repository | `@DataJpaTest` + Testcontainers | 10 | 0.45초 |
| Controller | `@WebMvcTest` + MockMvc | 20 | 0.4초 |
| 아키텍처 | ArchUnit | 12 | 0.3초 |
| 인증 | 순수 JUnit + MockHttpServletRequest | 8 | 0.33초 |
| 전체 흐름 | `@SpringBootTest` E2E | 7 | 0.74초 |
| 동시성·성능 | `@SpringBootTest` (Phase 3) | 6 | — |

도메인 테스트가 가장 많고 가장 빠르다. **풍부한 도메인 모델의 이점이 여기서 회수된다** —
불변식이 엔티티 안에 있으므로 DB도 웹도 없이 검증된다.

### curl E2E 48건은 남긴다

자동화 E2E(`ShopScenarioTest` 7건)로 **대체하지 않는다.** 검증 대상이 다르다.

| | 검증 대상 |
|---|---|
| `ShopScenarioTest` | 애플리케이션 내부 배선 — 컨트롤러·서비스·JPA·JWT가 이어지는가 |
| curl E2E 48건 | **배포된 프로세스** — 실제 소켓, 실제 HTTP, 실제 `Set-Cookie` 헤더, `docker compose`로 뜬 컨테이너 |

MockMvc는 **서블릿 컨테이너를 거치지 않는다.** 포트 바인딩, 리버스 프록시, `Secure` 쿠키가
실제 HTTP에서 어떻게 동작하는지는 잡지 못한다. Phase 5(HA 다중 인스턴스)·Phase 6(k6)에서
검증할 대상이 정확히 그 층이다.

또한 curl 스위트는 **기동 자체를 검증한다** — Phase 0 이식성 검증이 그것으로 이뤄졌다.

### 테스트 실행 시간과 `withReuse` 판단

- 전체 119건: **벽시계 73~78초**, 그중 **테스트 실행은 3.2초**
- 나머지는 Spring 컨텍스트 생성 + Testcontainers 기동

`.withReuse(true)`는 코드에 있으나 **실측 결과 효과가 없었다.**

| 조건 | 시간 |
|---|---|
| 재사용 opt-in 켬 (1회차) | 77초 |
| 재사용 opt-in 켬 (2회차) | 78초 |
| 재사용 opt-in 끔 | 73초 |

재사용된 컨테이너가 `docker ps`에 남지도 않았다. 컨테이너가 **Spring 빈으로 관리되어
컨텍스트 종료 시 함께 정리되기** 때문으로 보인다. 즉 **병목은 컨테이너가 아니라
Spring 컨텍스트 생성**이며(현재 컨텍스트 8~9개), 재사용 설정을 개발자에게 요구할 근거가 없다.

> 지금은 조치하지 않는다. 테스트가 늘어 시간이 문제가 되면 그때 **컨텍스트 수를 줄이는 쪽**
> (설정을 통일해 캐시 히트를 늘리는 것)을 먼저 본다 — 컨테이너 재사용이 아니라.

## 18. 계층별 테스트만으로는 층 사이가 빈다 (Phase 4 후속)

### 무엇이 빠졌나

Phase 4를 마친 시점에 예외·실패 분기를 전수 조사했다. `GlobalExceptionHandler`의 핸들러 6개 중
**2개가 어떤 테스트에도 진입하지 않았고**, 변이를 넣으니 **테스트 119건이 전부 통과**했다.

| 변이 | 결과 |
|---|---|
| 500 응답에 `e.getMessage()`를 실어 보낸다 | 아무도 못 잡음 |
| `ParameterException`을 400 대신 500으로 매핑한다 | 아무도 못 잡음 |
| `supportsParameter`의 `String` 타입 검사를 지운다 | 아무도 못 잡음 |

첫 번째는 **Phase 2 B-1에서 처리한 항목**이다 — "스택트레이스는 로그만, 응답엔 traceId".
그 결정이 **회귀를 막지 못하는 상태**로 두 Phase를 지나왔다.

### 원인은 하나다 — 각자 자기 층만 봤다

| 계층 | 무엇을 검증했나 | 무엇을 안 봤나 |
|---|---|---|
| Controller (`@WebMvcTest`) | Service 목이 **`ResponseException`을 던지는** 경우의 매핑 | 목이 던지지 않는 예외 종류 — `ParameterException`, 미처리 예외 |
| 도메인·Service | `ParameterException`이 **발생하는지** | 그것이 **HTTP 상태로 무엇이 되는지** |
| E2E | 정상 흐름 + 미인증 401 | 서버 내부 오류가 났을 때의 응답 |

**어느 층도 틀리지 않았다.** 각자 자기 책임 범위를 정확히 검증했고, 그 범위들이 만나는 자리가 비었다.

> 도메인 테스트가 `assertThatThrownBy(...ParameterException.class)`로 단언한 것은
> "이 상황에서 이 예외가 나온다"이지 "클라이언트가 400을 받는다"가 아니다.
> **예외의 발생과 예외의 표현은 다른 계약이고, 다른 층에 있다.**

### 조치 — 운영 코드는 그대로, 테스트만 추가

- `GlobalExceptionHandlerTest` 4건 — 500 응답에 예외 메시지·경로·스택트레이스 흔적이 없고
  `traceId`가 **요청마다 다른지**까지 단언한다 (고정 문자열이면 로그에서 사고를 구별할 수 없다)
- `LoginCustomerArgumentResolverTest` 5건 — `@LoginCustomer`가 붙어도 `String`이 아니면 거부

역검증 4건 전부 잡혔다.

### 다음에 같은 틈을 만들지 않으려면

계층별 테스트를 설계할 때 **"이 층이 만드는 것"이 아니라 "이 층을 통과해 나가는 것"** 을 기준으로 본다.
`ParameterException`은 도메인이 만들지만 **웹 계층을 통과해 나간다.** 만드는 쪽만 테스트하면
통과 경로가 검증되지 않는다.

실무적으로는 **예외 종류별 매핑 표(`SPEC.md` 4절)를 테스트 체크리스트로 그대로 쓰는 것**이 확실하다 —
표에 9줄이 있으면 검증도 9건이어야 한다.

## 19. Swagger 노출 범위 (Phase 5)

### 무엇을

`springdoc-openapi`를 붙이고 **켠 채로 제출한다.** `SWAGGER_ENABLED=false`로 끌 수 있게 두었다.

### 왜 켜는가

채점자가 Postman 설정 없이 **브라우저만으로 전체 API를 호출할 수 있어야 하고, 그것이 산출물의 일부**다.
`SPEC.md` 5절의 E2E 시나리오를 Swagger UI에서 순서대로 실행할 수 있다.

인증이 쿠키 기반이라 잘 맞았다 — `POST /api/customers/login`을 실행하면 브라우저가 `Set-Cookie`를
저장하고 이후 요청에 자동으로 실린다. 같은 오리진이라 `SameSite=Strict`에도 걸리지 않는다.
**토큰을 복사해 붙여넣는 절차가 없다.** (`HttpOnly`라 `Authorize` 버튼으로는 값을 넣을 수 없고,
`SecurityScheme`은 "어떤 엔드포인트가 인증을 요구하는가"를 표시하는 용도다.)

### 왜 스위치를 두는가

**문서는 곧 공격 표면의 지도다.** 엔드포인트·파라미터·에러 코드·인증 요구가 한 화면에 정리돼 나간다.
실서비스라면 끄거나 내부망에만 여는 것이 맞다. 지금 켜는 것은 **이 프로젝트의 목적에 따른 선택**이지
"공개해도 괜찮아서"가 아니다 — 그 구분을 코드에 남기려고 스위치를 뒀다.

## 20. 로그가 새 자산 경로가 된다 (Phase 5)

### 무엇을

API 로깅 AOP를 붙이면서 비밀번호 방어를 **두 겹**으로 만들었다.

| 겹 | 방법 | 막는 것 |
|---|---|---|
| 1 | 요청 DTO에 `@JsonProperty(WRITE_ONLY)` | 직렬화 자체에서 필드가 빠진다 |
| 2 | `SensitiveDataMasker` | `toString()`·쿼리스트링 등 다른 경로 |

### 왜 — Phase 2에서 "미점검"으로 남긴 자리

Phase 2 자산 점검에서 비밀번호의 **로그 경로는 "미점검"** 이었다. 응답 경로(DTO·`@JsonIgnore`)만
막았고, 그때는 **로그에 요청 바디를 찍는 코드가 아예 없었다.** 없는 경로는 점검할 수 없다.
API 로깅이 그 경로를 만드는 시점이 지금이다.

### ★ 첫 검증이 거짓 음성이었다

로그에 평문 비밀번호가 **0건**으로 나왔다. 그런데 마스커가 한 일이 아니었다 —
DTO에 `@ToString`이 없어 `CustomerRequest@327b3e8b`가 찍혔을 뿐이고,
**로그는 아무 정보도 남기지 않고 있었다.**

```
→ CustomerController.createCustomer (com.sk.skala...CustomerRequest@327b3e8b)
```

"비밀번호가 없다"와 "아무것도 없다"는 다르다. 마스커를 따로 시험해보고서야 알았다.
그래서 로그 캡처 테스트는 **두 가지를 함께 단언한다** —
비밀번호가 없다, **그리고 다른 필드는 있다.** 후자가 없으면 "아무것도 안 찍힘"도 통과한다.

### 테스트가 마스커의 실제 구멍을 잡았다

`authorization=Bearer <token>`에서 값의 공백을 끝으로 봐서 **`Bearer`만 가려지고 토큰이 남았다.**
구분자까지 삼키도록 고쳤다 — **로그에서는 과하게 가리는 쪽이 안전하다. 덜 가리면 그게 유출이다.**

### 한계 (테스트로 명시)

`@Valid` 실패와 인증 실패는 **컨트롤러 메서드 진입 전에** 터져 AOP에 잡히지 않는다.
`GlobalExceptionHandler`의 debug 로그가 담당한다. 요청 단위로 빠짐없이 남겨야 한다면
필터·인터셉터로 옮겨야 하고, 그때는 이 동작을 고정한 테스트가 깨지며 알려준다.

## 21. Actuator는 화이트리스트로만 연다 (Phase 5)

`include: health` 하나만 연다. `readiness`/`liveness` 프로브를 켜고 `show-details: never`.

**`include: "*"` 한 글자면** `/actuator/env`가 열리고 거기에 `JWT_SECRET`·DB 비밀번호가 그대로 보인다.
`/actuator/heapdump`는 힙 전체를 파일로 내려준다 — 메모리에 있던 평문 비밀번호와 토큰이 함께 나간다.
**Phase 2에서 막은 것과 같은 자산이고, 설정 한 줄로 되돌아간다.**

그래서 테스트가 **"닫혀 있어야 할 것"을 이름으로 단언한다**(`env`, `configprops`, `beans`, `mappings`,
`loggers`, `heapdump`, `threaddump`, `metrics`, `info`, `conditions`, `scheduledtasks` → 전부 404).
화이트리스트가 실수로 넓어지면 거기서 깨진다.

`liveness`와 `readiness`를 구분한 이유 — DB가 잠깐 끊겼을 때 **멀쩡한 프로세스를 재시작하지 않고
로드밸런서에서만 빼기** 위해서다. 하나로 합치면 그 구분이 사라진다.

## 22. 오프라인 빌드에 미리 대비하지 않는다 (Phase 5)

### 결론

**대비하지 않는다.** 대신 필요할 때 쓸 절차를 README에 남긴다.

### 왜

`docker compose up`은 베이스 이미지 풀과 Gradle 의존성 다운로드에 인터넷이 필요하다.
대응 방법은 셋 다 비용이 있다.

| 방법 | 비용 |
|---|---|
| 빌드된 jar를 저장소에 커밋 | **"소스에서 빌드된다"는 성질을 잃는다.** 바이너리와 소스가 어긋나도 알 수 없다 |
| 의존성을 저장소에 동봉 | 저장소가 수백 MB가 된다. 리뷰·클론이 실질적으로 어려워진다 |
| 이미지 tar를 별도 제출 | 제출 경로가 하나 더 늘고, 그 tar가 최신인지 보장할 방법이 없다 |

**채점 환경이 폐쇄망이라는 근거가 없다.** 진행 내내 이미지 풀과 의존성 다운로드가 전제였고
Phase 0 이식성 검증도 네트워크가 있는 환경에서 통과했다.
근거 없는 대비는 이 프로젝트가 반복해서 피해온 것이다 ("설정값에는 근거가 붙어야 한다").

### 대신 한 것

- **요구사항을 명시**했다 — README에 "네트워크가 필요하다"를 절로 분리했다.
  실패하더라도 원인을 모르는 채 헤매지 않게 하는 것이 최소한의 대비다
- **탈출구를 문서화**했다 — `docker save`/`load` + `--no-build` 절차.
  지금 비용은 0이고 필요할 때 바로 쓸 수 있다
- compose에 `image: ${APP_IMAGE:-...}`를 넣어 **미리 만든 이미지로 띄울 수 있게** 했다.
  이 한 줄이 롤백 절차와 오프라인 절차 양쪽에서 쓰인다

## 23. 배포 태그 전략과 롤백의 한계 (Phase 5)

### `latest`를 배포에 쓰지 않는다

`latest`는 **"지금 무엇이 떠 있는지"를 알려주지 못한다.** 같은 태그가 시점마다 다른 이미지를
가리키므로 "어제 것으로 되돌려라"가 성립하지 않는다.
배포 태그는 **커밋 해시**를 쓴다 — 코드와 이미지가 1:1로 대응되고 불변이다.

### 절차를 문서로만 남기지 않았다

README의 롤백 절차를 **그대로 실행해 확인했다** — 특정 태그로 빌드 → `APP_IMAGE`로 지정해 기동 →
`health: healthy` → 실제로 뜬 이미지 확인 → E2E 48/48.
그 과정에서 compose에 `image:` 키가 없으면 절차가 동작하지 않는다는 것을 발견해 추가했다.
**동작하지 않는 절차를 문서에 적는 것은 없는 것보다 나쁘다.**

### 롤백이 안 되는 것 — 스키마

애플리케이션은 되돌릴 수 있지만 **DB 스키마는 되돌아가지 않는다.**
현재 `ddl-auto: create`이라 재기동 시 스키마가 새로 만들어지고 데이터가 사라진다.
학습 프로젝트라 유지하지만, 실서비스라면 `validate` + 마이그레이션 도구가 전제이고
컬럼 삭제·타입 변경은 **추가 → 이행 → 제거**의 세 배포로 나눠야 롤백 가능한 상태가 유지된다.

## 24. 동시 첫 주문의 제약 위반은 500이 아니라 409다 (Phase 6)

### 무엇을

`DataIntegrityViolationException`을 **409 `CONCURRENT_MODIFICATION`** 으로 매핑했다 (커밋 `278b077`).
제약 이름과 테이블명은 응답에 싣지 않는다.

### 증상 — 집계가 가리고 있었다

부하 중 `POST /api/customers/order`에서 **요청당 1~9건의 500**이 나가고 있었다.
전체 집계로는 **"성공률 99.99%"** 라 묻혀 있었고, 풀 크기 스윕에서 `resp_5xx`를 **따로 세면서** 드러났다.

**소수점 아래에 숨은 결함이다.** 99.99%를 성공으로 읽는 한 영원히 보이지 않는다.

### 원인 — check-then-act 경합

같은 `(고객, 상품)` 조합의 **첫** 주문이 동시에 들어오면, 양쪽 트랜잭션 모두
`findByCustomerAndProduct`에서 빈 결과를 받는다. 그리고 양쪽 모두 INSERT를 시도한다.
`uk_order_items_customer_product` 복합 UNIQUE가 뒤쪽을 거부한다.

**"확인하고 나서 행동한다"는 순서 자체가 경합 지점이다** — 확인과 행동 사이에 남이 끼어든다.

### ★ `Customer`의 `@Version`은 이것을 막지 못한다 — 이유가 두 겹이다

| 이유 | 내용 |
|---|---|
| **다른 행이다** | 낙관적 락이 검사하는 것은 `customers` 행의 버전이다. 충돌하는 것은 `order_items` 행이고, 그 행에는 버전이 없다 |
| **검사보다 먼저 터진다** | PK 생성이 `IDENTITY` 전략이라 영속화 시점에 **INSERT가 즉시 실행**된다. 커밋 시점의 버전 검사에 **도달하기 전에** 제약이 걸린다 |

두 번째가 특히 비직관적이다. `SEQUENCE` 전략이었다면 INSERT가 flush까지 미뤄져
예외가 터지는 **시점과 순서가 달라진다**. 즉 **동시성 동작이 키 생성 전략에 좌우된다** —
JPA 매핑 선택이 성능이나 이식성만의 문제가 아니라는 뜻이다.

`@Version`을 `OrderItem`에 추가해도 해결되지 않는다. 낙관적 락은 **이미 존재하는 행의
동시 수정**을 막는 장치인데, 여기서 충돌하는 것은 **아직 존재하지 않는 행을 양쪽이 만들려는 상황**이다.
14절의 정정 블록에 같은 내용을 적어두었다.

### 왜 409인가

- **제약 위반은 정의상 상태 충돌이다.** 요청 자체는 올바르다. 500은 "서버가 잘못했다"는 뜻이라
  클라이언트가 재시도해도 되는지 알 수 없다
- **재시도하면 성공한다.** 상대 트랜잭션이 만든 행을 찾아 **수량 누적 경로**로 진입한다.
  즉 이것은 재시도 가능한 실패이며, 409가 말하는 바로 그 상황이다
- 14절의 낙관적 락 충돌과 **같은 부류**이므로 같은 에러 코드를 쓴다. 코드를 새로 만들지 않았다
- **의미를 아는 제약 위반은 여기까지 오지 않는다.** 삭제 시 참조 무결성(`DATA_IN_USE`, 9-6절)은
  각 Service가 먼저 잡는다. 이 핸들러가 받는 것은 **의미를 모르는 나머지**다
- **제약 이름·테이블명을 응답에 싣지 않는다.** `uk_order_items_customer_product`를 그대로 내보내면
  스키마 구조를 알려주는 셈이다 (9-3절 500 유출 차단과 같은 판단)

### 자동 재시도는 여전히 넣지 않는다

14절에서 `@Retryable`을 넣지 않은 이유가 그대로 적용된다 — 재시도 정책은 충돌 분포 측정 위에서
정해야 하고, 주문은 금전 거래라 클라이언트가 시도 횟수를 알아야 한다.
**409로 알리고 재시도 여부는 클라이언트에 맡긴다.**

### 회귀 테스트 2건 — "최소 1건은 성공하는가"를 함께 단언한다

| 테스트 | 무엇을 고정하는가 |
|---|---|
| `ConcurrentOrderTest` | 같은 상품 30스레드 동시 첫 주문 → 성공 4 / 제약위반 9 / 낙관적락 17. 발생한 예외가 **전부 409로 매핑되는 종류**인지, 즉 **"500이 될 예외"가 섞이지 않는지** 단언한다 |
| `GlobalExceptionHandlerTest` | 제약 위반 → 409, **제약명 미노출** |

첫 번째 테스트에 **"최소 1건은 성공한다"를 함께 넣었다.** 이것이 없으면 30건이 전부 실패해도
"모든 예외가 409였다"로 통과한다 — Phase 5에서 "비밀번호가 로그에 없다"가 *로그가 아예 없어서*
통과했던 것과 같은 형태다. **"나쁜 일이 없었다"는 단언에는 "일이 실제로 일어났다"가 붙어야 한다.**

### 검증

교정 후 같은 부하에서 **500 0건, 앱 ERROR 로그 0건.**

## 25. 상품 캐시와 HTTP 캐시 헤더 — 구현과 측정의 경계 (Phase 6)

### ★ 무엇이 검증됐고 무엇이 안 됐는가

**이 절의 가장 중요한 내용이다.** 두 기능은 Phase 3에서 "측정 근거가 필요하다"는 이유로
Phase 6까지 미뤄둔 항목인데, **구현과 기능 검증만 끝나고 성능 효과는 아직 측정하지 않았다.**

| 항목 | 상태 |
|---|---|
| 캐시 적재·무효화가 올바른가 | ✅ 테스트 3건으로 고정 |
| HTTP 헤더가 붙고 304가 나가는가 | ✅ 테스트 3건으로 고정 |
| 개인 데이터에 캐시 헤더가 안 붙는가 | ✅ 테스트로 고정 |
| **캐시가 실제로 빠르게 하는가** | ❌ **미측정** |
| **ETag가 전송량을 얼마나 줄이는가** | ❌ **미측정** |

**측정하기 전까지 "성능이 개선됐다"고 쓰지 않는다.** 이 프로젝트가 Phase 3에서 이 항목들을
미룬 이유가 정확히 그것이었고, 구현했다는 사실이 그 판단을 해제하지 않는다.
`docs/evidence/perf/README.md`의 "아직 하지 않은 것"에 같은 내용이 있다.

### 왜 상품만 캐시하는가

| 대상 | 판단 |
|---|---|
| **상품** | ✅ 읽기가 압도적이고, 쓰기가 드물며, **모두에게 같은 데이터**다 |
| 고객·주문 | ❌ 사용자마다 다르고 주문마다 바뀐다. 적중률이 낮고 무효화가 복잡하다 |

캐시는 **"같은 것을 여러 번 읽을 때"** 이득이 난다. 사용자별로 다른 데이터는 그 전제가 없다.

### 엔티티가 아니라 DTO를 캐시한다

엔티티를 캐시하면 **detached 인스턴스 하나를 여러 요청이 공유**한다.
지연 로딩 예외가 나거나, 한 요청이 만진 상태가 다른 요청에 보인다.
`open-in-view: false`와 같은 문제의식이다 — **영속성 컨텍스트 밖으로 엔티티를 내보내지 않는다.**

### `allEntries = true`를 쓰지 않는다

`key`를 지정해 **해당 항목만** 비운다. 전체를 비우면 상품 하나를 고칠 때마다
나머지 전부의 적중률이 무너진다. 무효화는 **정확한 만큼만** 한다.

### HTTP 캐시 헤더 — `max-age=60`의 근거는 측정값이 아니다

상품 상세에 `Cache-Control: public, max-age=60` + `ShallowEtagHeaderFilter`.

> **60초는 "가격 변경이 그만큼 늦게 보여도 되는가"로 정한 도메인 판단이다. 측정값이 아니다.**
> `CLAUDE.md`의 "설정값에는 측정 결과나 **명시적 근거**가 붙어야 한다"에서 후자에 해당한다.
> 측정으로 정할 수 있는 종류의 값이 아니라는 것까지 근거의 일부다 —
> 부하를 아무리 재도 "가격이 1분 늦게 보여도 되는가"는 나오지 않는다.

### ETag와 `@Cacheable`은 목적이 다르다

**ETag가 아끼는 것은 네트워크 전송뿐이다.** `ShallowEtagHeaderFilter`는 응답 본문을 **다 만든 뒤**
해시를 계산하므로, DB 조회도 직렬화도 그대로 일어난다. 304를 받아도 서버 일은 줄지 않는다.
`@Cacheable`은 그 앞단의 작업 자체를 건너뛴다. **둘을 "캐싱"으로 뭉쳐 말하면 안 된다.**

### ★ 개인 데이터에는 캐시 헤더를 붙이지 않는다

`Cache-Control: public`은 중간 캐시(프록시·CDN)에게 **보관해도 좋다**고 말하는 것이다.
잔액·주문 이력에 붙이면 **남의 개인정보를 중간 캐시가 들고 있게 된다.**
Phase 2에서 막은 자산이 헤더 한 줄로 새는 경로이므로 **테스트로 고정**했다.

### 한계 — 다중 인스턴스에서 전파되지 않는다

`ConcurrentMapCacheManager`는 **인스턴스별 로컬 캐시**다. app을 2개 띄우면 한쪽에서 상품을 수정해도
다른 쪽 캐시는 낡은 값을 그대로 준다. **HA 다중 인스턴스 구간에서 다뤄야 할 항목**이고,
그때 공유 캐시(Redis 등)로 갈지 TTL로 견딜지 판단한다.

### 테스트가 "빨라졌는가"보다 "무효화되는가"를 먼저 고정한 이유

**캐시는 틀린 값을 빠르게 주는 방식으로 실패한다.** 느려지는 실패는 눈에 띄지만
낡은 값을 주는 실패는 조용하다. 그래서 적재보다 **무효화**를 먼저 단언한다.

> 병목이 DB가 아니라 HTTP 처리·직렬화에 있다. **다만 이건 측정하지 않았고 추정이다.**

### ③ ETag — 이쪽은 명확한 효과가 있다

| | 전송량 | p95 | 2xx |
|---|---|---|---|
| 일반 GET | 7.4 MB | 2.86ms | 23,090 |
| **ETag 조건부 요청** | **3.6 MB (−51%)** | 3.08ms | **20** (나머지 304) |

**이 절이 "ETag가 아끼는 것은 네트워크 전송뿐"이라고 적은 것이 그대로 실증됐다.**
전송량은 절반으로 줄었고 **서버 응답 시간은 변하지 않았다**(1.45 → 1.49ms).

측정 장치도 먼저 검증했다 — `setup()`에서 ETag가 응답에 실제로 오는지 확인하고 없으면
중단한다. 없으면 "전송량이 안 줄었다"가 ETag의 실패인지 조건부 요청 미성립인지 구분되지 않는다.

|---|---|
| **이득** | **측정되지 않음** (상한 조건에서도 편차 안) |
| **위험** | 심각도 낮음(표시만) · 발생률 높음(인스턴스 수만큼) · **지속 무한** |

**선택지와 비용:**

| 선택지 | 비용 | 판단 |
|---|---|---|
| **`@Cacheable` 제거** | 코드·테스트 3건 삭제 | ✅ **근거상 가장 타당.** 이득이 없으므로 잃을 것이 없고 **결함이 함께 사라진다** |
| HA에서 기본 off | 0 (compose 기본값) | ✅ **즉시 적용 가능.** 위험이 나타나는 곳에서만 끈다 |
| 현상 유지 + 한계 명시 | 0 | ⚠️ **이득 없는 기능을 남긴다** — 이 프로젝트가 MyBatis를 도입하지 않은 근거와 충돌한다 |
| Redis 공유 캐시 | **새 인프라 1개** + 네트워크 홉 + 장애점 + 운영 부담 | ❌ **측정되지 않은 이득을 지키려고 인프라를 늘리는 것은 순서가 거꾸로다** |

**결론** — **이득이 없다는 것이 측정으로 확인됐으므로, 근거는 제거를 가리킨다.**
`docs/evidence/perf/win-detail-*.txt`.

다만 **측정은 이 환경의 것이다.** 상품 수가 많아지거나 조회가 무거워지면(조인·집계)
결론이 바뀔 수 있다. 재도입 조건을 적어둔다 —
**상세 조회가 단일 행 PK 조회를 넘어서거나, DB가 병목으로 측정될 때.**

**ETag는 유지한다.** 전송량 −51%는 측정된 이득이고, 낡은 값 문제가 없다
(`ShallowEtagHeaderFilter`는 매 요청 본문을 다시 만들어 해시하므로 서버 상태를 캐시하지 않는다).

### ⑤ 실행 — `@Cacheable`을 제거했다 (2026-08-08)

**지운 것**: `@Cacheable`·`@CacheEvict` 애노테이션, `CacheConfig`(`@EnableCaching` 포함),
`ProductCacheTest` 3건, `docker-compose.ha.yml`의 `SPRING_CACHE_TYPE` 스위치.
`application.yml`에는 `spring.cache.*` 설정이 애초에 없었다(자동 구성에 맡기고 있었다).

**ETag(`HttpCacheConfig`)는 손대지 않았다.**

#### 왜 B(HA에서만 off)가 아닌가

**단일 구성에서도 같은 결함이 남기 때문이다.** 낡은 값은 다중 인스턴스에서 *눈에 띄었을 뿐*,
기제는 단일에서도 동일하다 — 예컨대 DB를 직접 수정하거나 다른 경로로 데이터가 바뀌면
캐시는 여전히 낡은 값을 **무한히** 들고 있다.

> **환경별 비활성화는 결함을 고치는 것이 아니라 결함이 보이는 환경을 피하는 것이다.**
> "HA에서는 끄면 된다"는 처방은 결함의 존재를 인정하면서 그것을 설정 뒤에 숨긴다.
> 게다가 그 설정을 잊은 채 다중 인스턴스로 배포하면 결함이 그대로 돌아온다.

#### 왜 C(현상 유지)가 아닌가

**이득 없는 코드를 유지하는 데도 비용이 든다** — 애노테이션 3개, 설정 클래스 1개,
테스트 3건, 그리고 무엇보다 **"이 캐시는 왜 있는가"를 다음 사람이 다시 검토해야 하는 비용**이다.

이 프로젝트는 MyBatis를 도입하지 않으면서 *"기술을 목적 없이 추가하는 것"* 을 거부했다(11절).
**이득이 측정되지 않은 캐시를 유지하는 것은 같은 원칙을 반대 방향에서 어기는 것이다** —
추가하지 않는 것과 같은 이유로, 남겨두지도 않는다.

#### Redis는 그대로 기각

위 표의 근거를 유지한다 — **측정되지 않은 이득을 지키려고 인프라를 늘리는 것은 순서가 거꾸로다.**
제거 이후에는 지킬 이득 자체가 없으므로 논의도 성립하지 않는다.

#### ★ 같은 "캐싱"인데 하나는 남고 하나는 지워졌다

| | ETag (`HttpCacheConfig`) | `@Cacheable` |
|---|---|---|
| 아끼는 것 | **네트워크 전송** | 서버 부하(DB 조회·직렬화) |
| 측정된 이득 | **−51%** (7.4 → 3.6 MB) | **없음** (p95 효과 0) |
| 위험 | 없음 (서버 상태를 캐시하지 않는다) | 낡은 값, **만료 없음** |
| 판단 | **유지** | **제거** |

**이 절이 "캐싱으로 뭉쳐 말하면 안 된다"고 적은 구분이 그대로 판단으로 이어졌다.**
뭉쳐서 봤다면 "캐싱은 효과가 있다"(ETag의 −51%를 보고) 또는
"캐싱은 효과가 없다"(`@Cacheable`을 보고) 중 하나로 잘못 갔을 것이고,
어느 쪽이든 나머지 하나에 대해 틀린 결정을 했을 것이다.
**용어가 같다는 이유로 함께 측정하지 않은 것이 두 개의 다른 결론을 가능하게 했다.**

## 26. 설정 스윕 — 편차를 먼저 재고, 기본값은 아직 바꾸지 않았다 (Phase 6)

### 무엇을

`docs/perf/sweep.sh`로 설정을 바꿔가며 곡선을 그렸다. **한 점만 재고 "좋아졌다"고 하지 않는다.**

### ★ 반복 편차를 먼저 잰다 — 이것이 없으면 모든 차이가 신호로 보인다

같은 설정(`DB_POOL_SIZE=10`)을 3회 반복했다.

```
p95  6.26 / 5.75 / 5.61ms  →  폭 0.65ms
```

**이 값보다 작은 차이는 설정 효과로 읽지 않는다.** 측정의 첫 단계는 대상을 재는 것이 아니라
**측정기의 흔들림을 재는 것**이다. 이걸 건너뛰면 노이즈에 이름을 붙이게 된다.

### HikariCP 풀 크기 (VUS=50 / 45초)

| 풀 크기 | 성공률 | p95 | req/s | 409 충돌 |
|---|---|---|---|---|
| 2 | 99.99% | **3.54ms** | 1,163 | 40 |
| 5 | 99.99% | 3.95ms | 1,156 | 245 |
| 10 (기본) | 99.99% | 4.67ms | 1,142 | 404 |
| 20 | 99.99% | 5.54ms | 1,119 | 592 |
| 40 | 99.99% | 5.27ms | 1,134 | 469 |

**폭 2.00ms — 반복 편차(0.65ms)의 3배이고 단조 증가다. 신호로 본다.**

풀이 커질수록 **409 충돌이 40 → 592건으로 함께 는다.** 이것이 해석을 뒷받침한다 —
풀이 크면 동시에 진행되는 트랜잭션 폭이 넓어지고, 같은 고객 행을 노리는 경합이 늘어난다.
**두 지표가 같은 설명을 가리킬 때 비로소 원인을 말할 수 있다.**

> Phase 3에서 "Lost Update 손실량 88,000은 커넥션 풀 크기가 만든 값"이라고 적은 것과
> **같은 현상을 반대편에서 본 것**이다. 그때는 풀 크기가 경합 폭을 정한다는 사실이
> 측정값의 해석 제한이었고, 여기서는 그것이 측정 대상이 됐다.

### Tomcat 스레드

| 스레드 | 성공률 | p95 | req/s |
|---|---|---|---|
| 10 | 100% | **6.52ms** | 1,090 |
| 25 | 100% | 4.79ms | 1,137 |
| 50 | 100% | 4.82ms | 1,148 |
| 100 | 100% | 4.72ms | 1,121 |
| 200 (기본) | 100% | 5.37ms | 1,119 |

**10은 측정 가능하게 나쁘고, 25 이상은 전부 반복 편차 안이다.**
즉 이 부하 수준에서 **스레드 수는 변별되지 않는다** — "최적값을 찾았다"고 쓸 근거가 없다.
**변별되지 않았다는 것도 결과이며, 그대로 적는다.**

### ★ 기본값을 아직 바꾸지 않았다

스윕은 곡선을 그렸을 뿐이고 **`application.yml`의 기본값은 그대로다** (`DB_POOL_SIZE:10`,
`TOMCAT_MAX_THREADS:200`). 이유는 두 가지다.

- **이 워크로드는 쓰기 경합이 지배적이다.** "풀이 작을수록 p95가 좋다"는 결과를 그대로 채택하면
  읽기 위주 구간이나 더 큰 부하에서 풀 고갈로 뒤집힐 수 있다. 곡선 하나로 값을 확정하지 않는다
- **확정하면 재측정이 따라야 한다.** 바꾼 값으로 부하·스트레스·스파이크를 다시 돌려
  기준값과 비교해야 "튜닝했다"가 성립한다. 그 재측정이 아직 남아 있다

**측정했다는 것과 결론을 내렸다는 것은 다르다.** 지금 상태는 전자까지다.

### 이 스윕이 실제로 찾아낸 것은 튜닝값이 아니라 결함이었다

풀 크기별로 `resp_5xx`를 따로 세는 과정에서 **500이 나가고 있는 것**이 드러났다 (24절).
설정을 재려고 만든 장치가 결함을 찾았다 — **지표를 잘게 쪼개는 것 자체가 관측 능력이다.**

### [2026-08-08 후속] 머신을 옮겨 편차를 다시 쟀다 — 0.65ms → 1.91ms

**편차는 코드의 성질이 아니라 측정 환경의 성질이다.** 머신이 바뀌면 다시 재야 한다.

| 머신 | 커밋 | p95 3회 | 폭 |
|---|---|---|---|
| macOS · Apple M5(ARM) · Docker VM 10CPU/7GB | `278b077` | 6.26 / 5.75 / 5.61ms | **0.65ms** |
| **Windows · x86_64 · WSL2 · 12CPU/7.7GiB** | `50cd7ef` | **14.25 / 13.49 / 15.40ms** | **1.91ms** |

**편차가 약 3배가 됐다.** 두 머신의 절대값을 비교하는 것이 아니다 — 사양도 OS도 다르고
Docker가 WSL2를 경유해 I/O 특성이 다르다. **비교 대상은 "각 환경의 편차 폭"뿐이다.**

흥미로운 것은 **무엇이 흔들리는가**다.

| 지표 | 3회 결과 | 안정성 |
|---|---|---|
| 성공률 | 100.00% × 3 | 완전 안정 |
| req/s | 1,009 / 1,019 / 1,011 | 폭 1% — 안정 |
| **p95** | 14.25 / 13.49 / 15.40ms | **폭 13%** |

**처리량은 안정적인데 꼬리 지연만 흔들린다.** WSL2를 경유하는 I/O가 꼬리에 민감하다는 뜻으로 읽힌다.
평균이나 TPS만 봤다면 "안정적인 환경"이라고 결론냈을 것이다.

### ★ 이것이 앞선 스윕 해석을 무효로 만든다

macOS에서 풀 크기 스윕의 폭은 **2.00ms**였고, 편차 0.65ms의 **3배**라서 신호로 판정했다.

> **이 머신에서 2.00ms는 편차(1.91ms) 안이다.**
> 같은 폭이 나와도 **신호라고 말할 수 없다.**

즉 "풀이 작을수록 p95가 좋다"는 결론은 **macOS 환경에서만 근거를 가진다.**
이 머신에서 같은 주장을 하려면 셋 중 하나가 필요하다.

| 방법 | 내용 |
|---|---|
| 반복을 늘린다 | 3회 → N회로 늘려 편차 폭 자체를 좁힌다 |
| 값 범위를 넓힌다 | 편차보다 확실히 큰 차이가 나는 구간까지 벌린다 |
| **변별 불가로 결론낸다** | "이 환경에서는 풀 크기 효과가 측정 노이즈에 묻힌다"고 적는다 |

**셋 다 정당하다.** 어느 것을 택할지는 스윕을 실제로 돌려 폭을 본 뒤 정한다 —
지금 정하면 그것이야말로 근거 없는 결정이다.

> **편차를 먼저 재는 규칙의 값이 여기서 드러났다.** 편차를 재지 않고 스윕부터 돌렸다면,
> macOS에서와 비슷한 2ms 안팎의 폭을 보고 **같은 결론을 반복했을 것이다.**
> 그리고 그 결론은 이 환경에서 근거가 없다.
> **같은 숫자가 한 환경에서는 신호이고 다른 환경에서는 노이즈다.**

> ## ★★ [반증 — 2026-08-08 HA 측정] 아래 "특이 지표" 주장은 철회한다
>
> HA 구성에서 **`LB + 인스턴스 1대`** 를 대조로 재보니 결과가 이렇다.
>
> | 구성 | DB 동시성 폭 | 409 비율 |
> |---|---|---|
> | 직접 1대 (LB 없음) | 10 | 0.65% |
> | **LB + 1대** | **10 (동일)** | **2.02%** |
> | LB + 2대 | 20 | 2.33% |
>
> **동시성 폭을 전혀 바꾸지 않고 LB 홉만 추가했는데 409가 3.1배가 됐다.**
> 따라서 아래의 *"409는 DB 동시성 폭을 재는 **특이** 지표"* 라는 **인과적 일반화는 근거가 없다.**
>
> **유효한 것과 철회하는 것을 구분한다.**
>
> | 서술 | 판정 |
> |---|---|
> | 풀 스윕 안에서 409가 풀 크기에 단조 반응했다 | ✅ **관찰로서 유효** |
> | 스레드 스윕에서 409가 반응하지 않았다 | ✅ 관찰로서 유효 |
> | 동시성 폭이 409에 영향을 준다 | ✅ 유효하나 **작다** (LB+1 2.02% → LB+2 2.33%, +15%) |
> | **"409는 동시성 폭을 재는 특이 지표"** | ❌ **철회.** 다른 변수로도 3배 움직인다 |
>
> **그 분리는 지표의 성질이 아니라 그 실험이 다른 변수를 고정했기 때문에 생긴 것이다.**
> 스윕은 풀만 바꾸고 나머지를 고정했고, 그래서 깨끗한 단조 관계가 보였다.
> 조건을 벗어나자 관계가 무너졌다.
>
> **대체 설명("충돌 창 = 동시성 × 지속시간")도 성립하지 않는다.**
> 스레드 스윕에서 p95가 2배(7.22 → 14.79ms)로 늘었는데 409 비율은 0.90 → 0.85%로 **오히려 줄었다.**
> **두 모델이 다 깨졌고, 현재로선 기전을 설명하지 못한다.** 미해결로 남긴다 —
> 가르려면 동시성 폭과 지속시간을 각각 고정한 측정이 필요하다.
> 상세는 `docs/evidence/perf/ha-prediction.md`.
>
> **이 반증은 사전 등록한 예측이 빗나간 덕에 드러났다.** 예측을 측정 후에 적었다면
> 2.33%에 맞는 설명을 새로 붙였을 것이고 아래 일반화는 그대로 남았을 것이다.

#### ★ 논증의 형태 — 반응하지 않은 것이 증거다

> ⚠️ 아래 논증은 **위 반증 이후 조건부로만 유효하다** — "스윕이라는 고정 조건 안에서"가 전제다.
> 원문을 지우지 않고 남기는 이유는, 어떤 논증이 어디까지 갔다가 어디서 깨졌는지가 기록의 핵심이기 때문이다.

409가 풀에 반응한 것만으로는 "부하가 세지면 충돌이 는다"로도 읽힌다.
결정적인 것은 **스레드 스윕에서 움직이지 않았다는 사실**이다.

> 409가 일반적인 부하 지표였다면 **스레드 스윕에서도 따라 움직였어야 한다.**
> 움직이지 않았다 — 그래서 **"409는 DB 동시성 폭을 재는 특이 지표"** 라는 해석이 선다.
>
> 그리고 이 예측은 **데이터를 보기 전에 기전에서 나왔다.** 가설이 데이터를 사후에
> 맞춘 것이 아니라, 기전이 예측한 대로 나왔다. 두 스윕이 서로의 대조군이 된 셈이다.

#### 409를 정반대로 읽을 수 있었다

풀 2에서 409가 **가장 적다(0.08%)**. 이것만 보면 *"풀을 줄이면 충돌이 줄어든다"* 가 된다.

**틀렸다. 경합이 적은 것이 아니라 애초에 동시에 실행되는 트랜잭션이 2개뿐이다.**
같은 설정에서 p95는 3배 나쁘고 처리량은 29% 낮다.
**지표 하나만 보면 정반대 결론에 도달하는 사례**로 남긴다.

### macOS와의 역전 — 두 축 모두

| | macOS | Windows(WSL2) |
|---|---|---|
| **풀 2** | **3.54ms — 최선** | **46.32ms — 최악** |
| **스레드 10** | **6.52ms — 유일하게 나쁨** | **7.22ms — 유일하게 좋음** |

**기전** — WSL2를 경유해 **쿼리당 지연이 크다.** 처리량 ≈ 동시성 ÷ 지연이므로,
지연이 큰 환경에서 커넥션 2개는 50 VU를 감당하지 못한다. 커넥션 하나가 더 오래 붙잡힌다.
스레드 쪽은 반대 방향이다 — 지연이 커서 요청이 앱 안에 오래 머무는데,
스레드가 200개면 12 vCPU 위에서 스케줄 경합만 늘어난다.

> **한 축이 뒤집힌 것은 우연일 수 있다. 두 축이 모두 뒤집힌 것은 아니다.**

### 튜닝값 최종 판단 — 기본값을 유지한다

**측정하지 않은 것을 주장하지 않는다.** 근거를 정확히 적는다.

| 설정 | 판단 | 근거 |
|---|---|---|
| `DB_POOL_SIZE` = 10 | **유지** | **"10이 최적이라서"가 아니다.** 5~40 사이에서 **변별할 수 없으므로 기본값을 바꿀 근거가 없다.** 다만 **풀 2는 명백히 나쁘다** — 하한은 확인됐다 |
| `TOMCAT_MAX_THREADS` = 200 | **유지** | 스레드 10이 VU 50에서 유의하게 좋다. 그러나 **한 부하 수준의 한 점**이고, 스레드를 줄이면 **더 높은 동시 사용자에서 큐잉이 생긴다.** 이 데이터로 기본값을 바꾸는 것은 **이 절이 금지한 바로 그 일이다** |

#### VU 축 스윕을 하지 않는 이유

VU를 바꿔가며 봐도 **"이 머신·이 워크로드·이 부하 범위"의 결과**이며 환경 종속성은 그대로 남는다.
**두 축 모두에서 macOS와 결론이 뒤집힌 시점에 이미 결론은 나와 있다** —
값을 확정하는 것 자체가 잘못된 목표다.
축을 하나 더 늘리는 것은 **같은 결론에 도달하는 비용만 더하는 일**이다.

### ★ 이 측정의 최종 결론

> **"측정했으므로 값을 정했다"가 아니라 "측정했더니 튜닝값이 환경에 종속된다는 것을 알았다"이다.**

단일 머신 측정만 있었다면 **풀 2와 스레드 200을 확신 있게 틀렸을 것이다** —
macOS 곡선으로 풀을 2로 내렸다면 이 환경에서 p95 3배·처리량 −29%였고,
스레드는 macOS 근거로 200을 유지했는데 이 환경에서는 그게 가장 나쁜 축에 든다.

실무의 결론은 **배포 환경에서 측정해야 한다**는 것이고,
**이 프로젝트가 기본값을 유지하는 것은 그 결론의 귀결이다** — 게으름이 아니라
"측정 환경이 배포 환경이 아니다"라는 사실의 반영이다.

### 5xx 0건 — 회귀 확인

**양쪽 스윕 10회 전 구간에서 500이 한 건도 없다.**
macOS 측정 당시 풀 40에서 `resp_5xx: 8`이 찍혀 있었고, 그것이 24절의 동시 첫 주문 결함이다.
**다른 머신·다른 부하 프로파일에서 재발하지 않음을 확인했다.**
성공률·5xx는 설정 변별력은 없지만 **회귀 감시 지표로는 유효하다.**

## 27. HA 다중 인스턴스 — 앱 계층 수평 확장의 실증과 그 한계 (Phase 6)

### ★ 무엇을 실증했고 무엇을 실증하지 못했나

**"HA를 구현했다"가 아니다. "앱 계층의 수평 확장 가능성을 실증했다"가 정확하다.**

| 실증한 것 | 결과 |
|---|---|
| 무상태(JWT) — 인스턴스를 가로지르는 인증 | ✅ `.3`에서 로그인 → **`.4`에서 주문 성공**, 잔액 정확 |
| 요청 분산 | ✅ 양쪽 수신. 단일 커넥션 기준 **10/10 완전 교대** |
| traceId 전파 | ✅ `X-Trace-Id`가 LB를 통과 |
| 장애 내성 | ✅ 인스턴스 1대 정지 중 **60/60 성공, 실패 0** |
| **처리량 증가** | ❌ **실증 실패 — 오히려 줄었다** (아래) |

### 구성 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| LB | **nginx:1.27-alpine** | 설정 20줄. Traefik은 **Docker 소켓 마운트**가 필요해 컨테이너가 호스트 데몬을 제어하게 된다 — Phase 2의 노출 최소화와 어긋난다 |
| 인스턴스 | **`app1`·`app2` 명시** (스케일 아님) | nginx는 업스트림 호스트명을 **기동 시 한 번만 해석**한다. `--scale` + DNS 조합은 컨테이너 재생성 시 옛 IP를 계속 보는 **조용한 실패**를 만든다 |
| 포트 | **LB만 노출**, 앱은 호스트 포트 없음 | LB 우회 접근이 가능하면 "LB를 통해 동작한다"는 검증이 정직하지 않다 |
| 파일 | **독립 `docker-compose.ha.yml`** | 프로파일은 불가(`profiles` 없는 서비스는 항상 뜬다 → 한 줄 실행이 깨지거나 포트 충돌). 오버라이드도 불가(**`ports`는 병합이라 제거할 수 없다**) |
| 재시도 | **`non_idempotent` 넣지 않음** | 넣으면 `POST /order`가 재시도돼 **중복 주문**이 된다. 14절에서 서버 자동 재시도를 거부한 판단이 LB 계층에도 적용된다 |

### `X-Upstream-Addr`를 기본으로 켜지 않는다

인스턴스 식별에 `$upstream_addr`(내부 IP·포트)를 쓴다. **상시 노출하지 않는다.**

내부 토폴로지와 인스턴스 수를 알려주는 정보이고, 제약명을 409 응답에서 뺀 것(24절)·
스택트레이스를 traceId로 바꾼 것(9-3절)·Actuator 화이트리스트(21절)와 **같은 부류**다.
위험도가 크지 않다는 것과 **근거 없이 열어도 된다는 것은 다르다.**
이 헤더의 근거는 **측정**이지 운영이 아니므로 `LB_EXPOSE_UPSTREAM=1`일 때만 붙인다.
기본 구성에서 **헤더가 실제로 없는 것을 검증**했다 — 껐다는 서술만 남기지 않는다.

### 처리량 — 늘지 않고 줄었다

| 구성 | req/s | p95 | 409 비율 |
|---|---|---|---|
| 직접 1대 (LB 없음) | **1,003** | 14.72ms | 0.65% |
| LB + 1대 | 981 (**−2%**) | 18.68ms | 2.02% |
| **LB + 2대 (HA)** | **814 (−19%)** | **46.96ms (3.2배)** | 2.33% |

**대조를 두어 원인을 갈랐다.** LB 홉 자체는 −2%로 미미하다.
**하락의 대부분은 두 번째 인스턴스가 만든다**(981 → 814, −17%).

**이 머신에서 인스턴스를 늘리면 용량이 늘지 않고 나뉜다.**
12 vCPU 하나 위에서 **app 2개 + nginx + postgres + k6가 전부 돈다.**
`evidence/perf/README.md`가 처음부터 적어둔 해석 제한 —
*"앱·DB·부하 생성기가 한 머신의 자원을 나눠 쓴다"* — 가 정면으로 드러난 것이다.

> **이것은 설계의 실패가 아니라 측정 환경의 한계다.** 그리고 그 구분을 수치로 말할 수 있게 된 것이
> 이 측정의 산출물이다. 수평 확장의 처리량 이득을 보이려면 **인스턴스가 서로 다른 물리 자원에
> 놓여야 한다.** 26절의 "튜닝값은 환경에 종속된다"와 같은 결론의 다른 얼굴이다.

### ★ 단일 지점 — 여전히 남아 있다

| 계층 | 상태 |
|---|---|
| 앱 | ✅ 2대. 하나가 죽어도 서비스 유지 확인 |
| **DB** | ❌ **단일.** 죽으면 전체 중단. 복제·페일오버 없음 |
| **LB** | ❌ **단일.** nginx가 죽으면 앱이 살아 있어도 접근 불가 |
| 캐시 | ⚠️ 인스턴스별 로컬 — 아래 |

**진짜 HA에 필요한 것** — ① DB 이중화(스트리밍 복제 + 자동 페일오버, 또는 관리형 DB)
② LB 이중화(VIP/keepalived 또는 클라우드 LB) ③ 무중단 배포(롤링 업데이트 + 커넥션 드레이닝).
현재는 **셋 다 없다.**

### `ddl-auto: create`는 다중 인스턴스와 양립하지 않는다

**기동할 때마다 스키마를 지우고 다시 만든다.** 다중 인스턴스에서는:

- **초기 기동이 경쟁 상태다** — 두 인스턴스가 동시에 스키마를 만든다
- **한 인스턴스만 재시작해도 공유 DB가 통째로 초기화된다** → **롤링 재시작이 불가능하다**

학습 프로젝트라 유지하지만(23절), **무중단 배포를 논하려면 이것부터 `validate` + 마이그레이션으로
바꿔야 한다.** HA 구성이 이 제약을 드러냈다.

### 로컬 캐시 — 25절의 예고가 실증됐다

25절이 *"다중 인스턴스에서는 수정이 다른 인스턴스에 전파되지 않는다"* 고 적어둔 그대로 재현됐다.
가격을 1000 → 7777로 바꾸고 12회 조회하니 **6/6으로 갈렸다** — 수정을 처리한 인스턴스는 7777,
다른 인스턴스는 1000.

**다만 영향 범위가 좁다.** `@Cacheable`은 `getProductById()`(응답 DTO)에만 걸려 있고
**주문 경로는 `findProduct()`로 DB를 직접 읽는다.** 즉 **결제 금액은 영향을 받지 않고**,
낡은 값은 **조회 표시에만** 나타난다.

**판단 — 지금 고치지 않는다. 근거를 남긴다.**

| 안 | 판단 |
|---|---|
| Redis 공유 캐시 | ❌ **측정되지 않은 이득을 지키려고 인프라를 늘리는 것은 순서가 거꾸로다.** 캐시의 성능 효과는 아직 미측정이다(25절) |
| TTL(Caffeine) | ⏸ 보류. 의존성 추가가 필요하고, 역시 이득이 측정된 뒤에 판단할 일 |
| **`SPRING_CACHE_TYPE=none`** | ✅ **탈출구로 제공.** compose 스위치로 노출했고 **실제로 동작하는 것을 확인**했다(끄면 양쪽 모두 최신값) |
| 현상 유지 + 한계 명시 | ✅ 이 프로젝트의 선택 |

> **이 판단이 이후 "캐시 성능 효과 측정"의 대상을 바꾼다.**
> 단일 인스턴스에서 캐시 이득을 재는 것은 여전히 유효하지만,
> **다중 인스턴스에서는 "이득"과 "낡은 값을 줄 확률"을 함께 재야 한다.**
> 이득이 작으면 캐시를 제거하는 것이 가장 단순한 해법이 된다 — 결함도 함께 사라진다.

### 예고된 함정 중 하나는 발동하지 않았다

`JOURNAL` Phase 5가 *"`depends_on: service_healthy`로 다른 서비스가 app을 기다렸다면
**기동이 무한 대기**한다. HA 구성에서 정확히 그렇게 된다"* 고 예고했다.

**말로 두지 않고 app2가 절대 healthy가 될 수 없게 만들어 확인했다.**

```
dependency failed to start: container skala-shop-api-app2-1 is unhealthy
compose exit=1, 24초
```

**무한 대기가 아니라 오류 종료다.** Compose v2는 의존 서비스가 `unhealthy`로 확정되면 중단한다.
다만 **조건부다** — 헬스체크가 *실패로 확정*돼야 한다. 실제 설정
(`start_period 40s / interval 10s / retries 5`)에서는 확정까지 **약 90초**가 걸리므로
"무한"은 아니어도 **느리다**. 헬스체크가 응답 없이 매달리는 형태라면 이야기가 달라진다.

### nginx 워커마다 상태가 따로다 — 두 곳에서 드러났다

`worker_processes auto` = **12개**(CPU 수). 그리고 **라운드로빈 커서와 `max_fails` 실패 카운터가
워커마다 독립적이다.**

- **분산 편중** — 매번 새 커넥션으로 40회 보내니 25/15. 단일 keep-alive 커넥션으로는 **10/10 완전 교대**
- **차단기 약화** — 인스턴스를 내린 뒤 30초 내내 **2~3초 간격으로 재시도가 계속 발생**한다.
  `max_fails=3`이면 곧 제외돼야 하지만, 각 워커가 독립적으로 3회를 채워야 하므로 잘 채워지지 않는다

**클라이언트에는 영향이 없었다**(전부 200). 그러나 **설정이 말하는 것보다 차단기가 약하게 동작한다** —
죽은 인스턴스가 *즉시 연결 거부*하면 비용이 작지만, **매달리는 형태로 죽으면**
`proxy_connect_timeout 2s`를 매번 물게 된다. 후자는 측정하지 않았다.
